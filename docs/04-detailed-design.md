# DistribuTAK の詳細設計

ADR 0030（`PRC-163:docs/decisions/0030-device-as-lan-router.md`）で決まった値と方式だけを書きます。部品の分け方とデータの流れは `03-basic-design.md` にあります。

決まっていない値は、推測で埋めずに 9 章の要確認の表に書きます。そこにある値は、利用者に確かめ、答えを先に ADR 0030 に書いてから、この文書に書き足します。

## 1. 暗号の組み合わせ

| 用途 | 方式 | 出典 | 根拠 |
|---|---|---|---|
| 握手の型 | `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s`（WireGuard と同じ） | NW1・NW2 の 5.4 節 | 答え 19・33 |
| 鍵の交換 | X25519 | CR7（RFC 7748） | 答え 20・33 |
| 暗号と改ざんの検出 | ChaCha20-Poly1305 | NW10（RFC 8439） | 答え 33 |
| ハッシュ | BLAKE2s | NW11（RFC 7693） | 答え 33 |
| 身元の鍵の署名 | Ed25519 | NW18（RFC 8032） | 答え 14・20・119 |
| 新しいグループの鍵と、入るときの証明書・グループの鍵を包む | HPKE。DHKEM(X25519, HKDF-SHA256)・HKDF-SHA256・AES-128-GCM、base モード | CR7（RFC 9180） | 答え 59・60・67 |
| 管理者の鍵の署名 | Ed25519（身元の鍵とは別の鍵） | NW18（RFC 8032） | 答え 71・119 |
| 鍵をしまうときに包む | Android の Keystore の取り出せない AES の鍵 | NW17 | 答え 73 |

- どれも公開標準です。実装は、よく知られたライブラリを使います（答え 11。DT-CN-02）。
- 暗号のライブラリは Bouncy Castle（Java）にまとめます（答え 72。NW16）。X25519・Ed25519・ChaCha20-Poly1305・BLAKE2s・AES-128-GCM・HKDF-SHA256・HMAC-SHA256 をここから使います。
- Noise（NW1）と HPKE（CR7）は、これらの部品から、それぞれの仕様のとおりに組み立てます。試験のベクトル（HPKE は CR6）で確かめます（答え 72）。
- Noise の試験のベクトルは、Noise の実装（cacophony、snow など）が公開しているもののうち、`Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s` のものを使います。どれを使うかと出どころは、作るときに確かめて `PRC-163:docs/references.md` に書きます（答え 78）。
- 暗号は、EUD の IP（Wi-Fi の LAN・モバイル回線）の上だけで使います。`AMATEUR` の電波区間には出しません（答え 11。DT-CN-01）。
- Ed25519・SHA-256・HMAC・AES-GCM・HKDF の出典は、references の NW18〜NW22 に足しました（答え 119）。NW3〜NW5 は欠番のままです。

## 2. 鍵

| 鍵 | 方式 | 持つもの | 根拠 |
|---|---|---|---|
| 身元の鍵 | Ed25519 | 端末ごとに 1 つ。端末の ID のもとになる | 答え 20・46 |
| 握手の鍵 | X25519 | 端末ごとに 1 つ。身元の鍵で署名する。作り直しても身元は変わらない | 答え 20 |
| グループの鍵 | 握手の psk | グループごとに 1 つ。メンバーを外したら作り直す | 答え 21・59 |
| 管理者の鍵 | Ed25519（身元の鍵とは別） | 管理者ごとに 1 つ。証明書・失効の一覧・管理者の一覧に署名する。公開鍵は管理者の一覧に載せる | 答え 22・28・71 |

- URL と QR コードには、相手の握手の鍵を短くせずにそのまま入れます（答え 20）。
- 端末の ID は、身元の鍵（Ed25519）の公開鍵の BLAKE2s-256 です（答え 46・70。NW11）。
- 身元の鍵・握手の鍵・グループの鍵・管理者の鍵は、Android の Keystore の中の取り出せない AES の鍵 1 つで包んでから、プラグインの保存場所にしまいます（答え 73。NW17）。Ed25519・X25519 を Keystore に直接しまえない端末でも動きます。
- 包む鍵は Keystore の AES-256-GCM（タグ 128 ビット。IV は Keystore が作る）です。利用者の認証と StrongBox は求めません。ATAK を起動し直したときに読み戻せるようにするためです（答え 163 の 1）。そのため、ハードウェアで守るとは画面にもドキュメントにも書きません。
- 保存の場所は、ホストの application Context の `getNoBackupFilesDir()/distributak/` です。ATAK の UID の内部の領域で、ATAK の中のほかのコードからは隔てられません（答え 163 の 2）。招待・TOTP の秘密の値・URL・セッションの鍵・クッキーはしまいません（答え 163 の 1）。開けないときは止めて、自動で作り直しません（答え 163 の 2）。加入した側は、最初の握手が終わるまで、招待にあった管理者の握手の公開鍵と番地（どちらも公開の値）を包んだ状態に入れ、口を開き直すときに pin を作り直します。最初の握手で相手の証明書と番地を保存できたら、この記録は消します。加入が確定しなかったときの保存は残しません（答え 163 の 11）。

## 3. 握手

### 3.1 1 通目

- 1 通目には、時刻の値と自分の証明書のほかは入れません。CoT などの中身は、握手が終わってから送ります（答え 19）。
- 時刻の値は、WireGuard と同じ TAI64N の形にし、暗号の中に入れます（答え 19。NW2 の 5.1 節）。
- 受ける側は、相手ごとに、受けた中でいちばん新しい時刻の値を覚えます。その値以下の 1 通目は捨てます（答え 19）。
- 時刻の値は、相手ごとに増えていれば受けます。自分の時計との差に上限は付けません（答え 53）。
- 受ける側は、1 通目の中の証明書を確かめ、グループの外の EUD を弾きます（答え 21・22）。確かめる中身は 4.1 にあります。
- 1 通目の中身（Noise のペイロード）は、TAI64N の時刻の値（12 バイト）のあとに証明書のバイト列を続けたものです（答え 128）。
- 時刻の記録は、いまの核（PRC-21.8）では証明書を確かめる前に確定します。証明書を確かめてから確定する形と、記録の数の上限（または相手ごとに消すこと）は、証明書を作る段で足します（ADR 0030 の「まだ決まっていないこと」）。

### 3.2 2 通目

- 2 通目の終わりで、グループの鍵（psk）が混ざります（答え 21。NW1 の 9.4 節）。グループの鍵を持たない EUD は、握手を終えられず、中身を復号できません。
- 受ける側は、2 通目に自分の証明書を入れます。形は 1 通目と同じです。握手を始めた側は、その証明書を 4.1 の 5 つで確かめてから、CoT などを送ります（答え 102）。
- 握手のときに、相手との時刻の差を測ります（答え 46）。測った差の使い方は 6 章にあります。
- 2 通目の中身も、1 通目と同じく TAI64N の時刻の値（12 バイト）のあとに証明書のバイト列を続けたものです。2 通目の時刻は、時刻の差を測るだけに使い、時刻の記録（3.1）には使いません（答え 128）。
- 1 通目・2 通目を読むのに失敗したら、その握手は閉じ、握手の状態を消します（答え 131。NW1 の 5 章）。

### 3.3 握手のあと

握手が済んだあとの相手ごとの鍵は、WireGuard の値で作り直します（答え 74。NW2）。値は資料で照らし合わせていません。

| 項目 | 値 |
|---|---|
| 握手し直す | 2 分たったら |
| 使わない鍵 | 3 分より古い鍵 |
| 作り直す送った数 | 2^60 通 |
| 受けない送った数 | 2^64 − 2^13 − 1 通を超えたら（ちょうどの値までは使う。答え 131） |

握手のあとの通信は、読めなかったもの（改ざんなど）を捨てて続けます。捨てたもので番号や鍵は変わりません（答え 131）。

相手が失効の一覧に載ったとき、相手の鍵が新しい鍵に変わったとき、相手の証明書の期限が切れたときは、その相手とのセッションをすぐに閉じます（答え 81）。「新しい鍵」は、証明書に入っている握手の鍵だけです。上の表の作り直す鍵（相手ごとに 2 分おき。答え 74）と、グループの鍵の作り直しは、すぐに閉じる条件には入れません（答え 95）。グループの鍵を作り直したときは、残るメンバーと新しい鍵で握手し直します（4.3。答え 81）。新しい鍵での握手が済んだ相手から、古い鍵で張ったセッションを閉じます。済むまでは古いセッションを使い続けますが、使える時間に上限を置き、過ぎたら閉じます。上限は 180 秒です（答え 108・110）。

### 3.4 メンバーどうしのセッションの細目

第5段（PRC-21.13）で決めた細目です。正本は ADR 0030 の答え 153〜157 です。ここでは要点だけを書きます。核の中だけで作り、ソケット・送信はまだ作りません。

- **パケットの形**: 40 バイトの枠（`DTK` と版 1・種類・16 バイトのセッションの識別子・グループの鍵の版・DATA の番号）のあとに、Noise の握手のメッセージか転送の暗号文を続けます。DATA の枠全体を暗号の AAD にします（答え 153 の 1）。
- **番号の窓**: 受けた最大の番号と、その手前 2048 個ぶんを覚えます。認証が通ってから窓を進めます（答え 153 の 2）。
- **大きさ**: 1 つのパケットは 1232 バイトまで、DATA の平文は 1176 バイトまでです。超える平文は、分割を作るまで送らずに断ります（答え 153 の 3・155）。分割は CoT の同期の段（第10段）で作ります（答え 166 (3)）。
- **送り直し**: 1 つの試み（送ると決めてから 90 秒）のあいだ、1 通目は 5 秒に 1 通まで（最大 18 通）です。2 通目を確かめられずに握手を作り直しても、試みの開始時刻と間隔を引き継ぎます。90 秒であきらめ、次に送るときに核が新しい握手を始めます。送れなかった中身は預かりません（答え 153 の 4・12・14、答え 154）。
- **受けた側の完了**: 受けた側は、始めた側から新しい鍵で認証の通ったパケット（始めた側が送る空の DATA）を初めて受けたときに切り替えます（答え 153 の 5）。
- **同時に始めたとき・張れたあとの新しい 1 通目**: 握手中なら公開鍵の小さい側の握手を残します。張れたあとに届いた新しい 1 通目は、証明書と時刻の記録が通れば未確認の候補で答え、確認が来るまで張れたセッションを残します。1 つの 1 通目への 2 通目は 18 通までです（答え 153 の 6）。
- **古い鍵と新しい鍵**: 相手ごとに、張ったセッション 1 つと候補 1 つまでです。切り替えたら古い鍵はすぐ 0 で埋め、遅れて届いた古い鍵のパケットは捨てます（答え 153 の 7・156）。
- **時計と呼び出し**: 核はタイマーのスレッドを持たず、呼び出し元が `refresh` と `poll` を呼びます。5 秒・90 秒・2 分・3 分・180 秒は単調な時計で比べます（答え 153 の 8）。時計を戻した直後の時計の差のずれは受け入れ、表示は目安にします（答え 153 の 9・157）。
- **証明書の発行の順**: 覚えている証明書より発行の古い証明書は断ります。このため、新しい証明書を先に覚えた側は、相手が新しい証明書を覚えるまで、前の証明書を出す相手と握手しません（答え 153 の 11）。
- **グループの鍵を作り直したとき**: 張れたセッションを持つ相手と、握手中・確認待ちの相手だけと新しい版で握手し直します。一度も握手していない相手・90 秒であきらめた相手・セッションを失った相手・失効した相手とは、次に送るときに握手します。確認待ちの候補しかなかった相手には、作り直しの時点から自分の新しい試みを始めます（90 秒はそこから数え、続けて作り直しても延ばしません）。前に 90 秒であきらめた相手でも、作り直しのときに確認待ちの候補を持っていれば予定に入れます（答え 153 の 13）。
- **数の上限**: 覚える相手はグループの台数の上限 −1 台まで、セッションと握手の状態は合わせてその 2 倍までです（答え 153 の 10）。
- **残る制約**（第5段の再レビューの申し送り。DoS 対策のクッキーなどのあとの段で見直します）:
  1. 相手が 90 秒であきらめた本物の 1 通目が遅れて届くと、受けた側は候補を作り、候補が 90 秒で消えるまで自分から握手を始められません。候補が消えたあとに送ろうとすれば新しい握手を始めます。相手から新しい 1 通目が来ればすぐ回復します。同じ 1 通目で起こせるのは 1 回だけです。
  2. 相手の記録に自分の 1 通目の時刻が残っているときに時計を戻して起動し直すと、記録より新しい時刻になるまで握手が通りません（1 通目の時刻の記録の規則。3.2）。戻した幅が経過した時間より大きいと、そのぶん長く通りません。
  3. 確認の DATA が失われ、そのうえ相手が起動し直したときは、候補だけを持つ側は最大 90 秒、自分から握手を始められません。相手から新しい 1 通目が来ればすぐ回復します。

### 3.5 UDP の口

第6段（PRC-21.14）で、3.4 のセッションを 1 つの UDP の口に載せました。正本は ADR 0030 の答え 158 です。ここでは要点だけを書きます。試験は PC のループバック（127.0.0.1 と ::1）だけで行い、外の網・実機・無線は使っていません。

- **受ける形**: 65535 バイトの入れ物で受けて長さを見て、1232 バイトを超えるものは切り詰めずに捨てます。`DTK` 版 1 の枠でないもの・短いものは、暗号の処理の前に捨てます（答え 158 の 1）。
- **スレッド**: 受けるスレッド 1 本と、250 ミリ秒おきに `refresh`・`poll` を呼ぶ時計のスレッド 1 本です。届いた平文は核のロックの外で受け口（コールバック）に渡し、戻ったら 0 で埋めます。受け口が戻らないと `close` も戻りません（答え 158 の 2）。
- **閉じ方**: 呼び出し元の `close` のほか、自分の証明書が失効・期限切れになって核が閉じたとき、受けるソケットが壊れたとき、時計の処理が壊れたときも、口は自分で閉じます（ソケットとスレッドを止め、鍵を 0 で埋める）。閉じたあとの `send` は false を返します。閉じた理由は照会で分かります。上の層に知らせる合図はあとの段で決めます（答え 158 の 3）。
- **相手の番地**: 認証と番号の窓を通った新しい DATA でだけ、相手の番地を変えます。1 通目・2 通目・改ざんしたもの・重ねて届いたものでは変えません。DATA の前に相手の番地が変わったときは、上の層が番地を覚え直します（答え 158 の 4）。
- **管理の一覧**: 管理者の一覧・失効の一覧の採用と `refresh` を同じロックの中で順に行います。口には、`SessionManager` を作ったときと同じ管理の状態を渡します（答え 158 の 5）。
- **送り直さない**: 届いた中身は受け口に渡すだけで、ほかの相手へ送る道はありません。A から B への中身が C に届かないことを試験で確かめています（答え 158 の 7。legal Q107 (2)）。
- **重さ**: 50 台の相手で `refresh`・送る・受けるの平均は約 4.8 ミリ秒でした（PC で測った値。Android では測っていない。答え 158 の 8）。
- **DoS 対策のクッキー**: 第8段で作りました（答え 160。下の段落）。

第7段（PRC-21.15）で、入るためだけの握手（4.4）も同じ口に載せました。正本は ADR 0030 の答え 159 です。試験はやはり PC のループバックだけです。

- **見分け方**: 入る握手は別の頭 `DTJ` の版 1 で送ります。見出しは 64 バイト、断片の中身は 1168 バイトで、パケットは 1232 バイト以下です。`DTK` の版 1 は上のとおりに処理し、知らない頭は捨てます。求め（最大 433 バイト）は 1 つのパケットに収まります（答え 159 の 1）。
- **返事の送り方**: 管理者は求めに 64 バイトの READY だけを返し、入る側が番号で取りに行く FETCH 1 通につき返事の断片を 1 通返します。送る量が受けた量を超えないので、偽の送り元の番地で他人に大量に送らせることはできません。最初の求めの番地に固定し、速度にも上限を置きます（答え 159 の 2）。
- **確かめ方**: 断片ごとには確かめず、組み立てたあとに HPKE と署名で全体を確かめます。壊れていたら 2 回まで全体を取り直します（答え 159 の 3）。
- **時間**: 返事を 10 秒持つこと（答え 113）、1 秒おきに 5 回まで送り直すこと（答え 150 の 8）は変えていません（答え 159 の 4）。
- **秘密**: 口は管理者の秘密を持ち続けず、求めのたびに呼び出し元から受け取り、使い終わったら 0 で埋めます。重い処理は別のスレッドで行い、メンバーどうしの受信を止めません（答え 159 の 7）。
- **入ったあと**: 入る側は、同じソケット・同じ番号のまま、メンバーどうしのセッションに移ります（答え 159 の 8）。管理者の側の呼び出し元には、出した証明書と新しいメンバーの公開鍵を渡します。一覧に載せて配るのは呼び出し元の仕事です（答え 159 の 9）。
- **送り直さない**: 届いた入るための求め・返事と握手の求め・返事を、ほかの相手へ送り直したり預かったりしません（答え 159 の 10。legal Q107 (2)）。DHT の記録は別で、5.3 の範囲で預かります（答え 181 の 6）。
- **残る課題**: 16 MiB に近い返事は、外の網では 10 秒に収まらない見込みです。偽の断片を差し込み続ける相手への備えも含めて、外の網の段で見直します（ADR 0030「第7段のあとの段で決めること」）。

## 4. 証明書と管理の記録

### 4.1 証明書

| 項目 | 値 | 根拠 |
|---|---|---|
| 署名する人 | 管理者の一覧に載った管理者 | 答え 22・28 |
| 中身 | メンバーの身元の鍵と握手の鍵、身元の鍵で握手の鍵に付けた署名、期限 | 答え 22・97 |
| 期限 | 30 日 | 答え 24 |
| 更新を始めるとき | 残りが 3 分の 1 ほど（10 日ほど）になったとき。管理者に届くときに自動で行う | 答え 24 |
| 管理者に 30 日届かなかったとき | 期限が切れ、グループのほかの EUD とつながらなくなる | 答え 24 |
| 画面に出すもの | 自分の証明書の残りの日数と、自動の更新の回数だけ。期限の時刻・鍵の値は出さない | 答え 178 (3) |
| 実機での更新の確かめ | 試験のグループ（2026-11-13 に作り直した）の更新が始まる 2026-12-03 ごろに行う。期限を短くする・しきい値を下げる切り替えは作らず、核の試験は差し替えた時計で確かめる | 答え 178 (4) |

握手の 1 通目を受けた側と、2 通目を受けた始めた側は、証明書について次の 5 つを確かめます（答え 22・28・84・85・97・102）。

1. 管理者の一覧に載った管理者が署名している。
2. 失効の一覧に載っていない。
3. 期限の中にある。期限は、自分の EUD の時計で比べる（答え 85・98）。発行の時刻が自分の時計より先でも 5 分までなら受けます。期限の終わりには余裕を付けません（答え 143）。
4. 相手の握手の鍵が、証明書に入っている握手の鍵と同じ（答え 84）。

### 4.4 入り直しの手順

- 新しいメンバー、新しいグループの鍵を受け取れなかったメンバー、証明書の期限が切れた EUD は、TOTP の URL（または QR コード）で管理者の EUD へ直接つなぎます（答え 60〜62）。
- URL の TOTP の値で「入るためだけの握手」をします。TOTP の値が正しければ、管理者の EUD は自動で（答え 149）、証明書とグループの鍵を、入る側の握手の鍵に向けて HPKE（4.3 と同じ組み合わせ）で包んで送ります（答え 60・67）。
- 「入るためだけの握手」のメッセージも Protocol Buffers で並べます（答え 88）。項目と細目は答え 150 で決めました（`core/src/main/proto/join.proto`）。求めは URL の握手の鍵へ、返事は入る側の握手の鍵へ、どちらも HPKE base で包みます（Noise の握手は使いません）。求めには、招待の秘密から作った鍵の HMAC（秘密を知っている証明）と TOTP を入れます。返事は URL の管理者が招待と求めに結び付けて署名し、起点からの管理者の一覧の鎖・いちばん新しい失効の一覧・証明書・包んだグループの鍵を入れます。前方秘匿はありません（答え 151 で受け入れた）。鎖は 64 件、返事は 16 MiB までです（答え 152）。
- 入るためだけの握手は、1 秒おきに 5 回まで送り直します（答え 87。仮の値で、試験で直します）。
- 管理者は、同じ求め（同じ鍵、同じ TOTP の値）の送り直しには、短い時間のあいだ、同じ返事をもう一度返します。別の鍵からの求めは断ります。同じ返事を返す時間は 10 秒です（答え 93・113）。これは新しく入る求めを受けることではなく、前に出した返事をもう一度返すことなので、TOTP の値を 2 度目に受けることには入りません（5.1）。同じ返事を返すために、管理者の EUD は、入る側の鍵、使った TOTP の値、出した返事を、同じ返事を返す時間のあいだだけ残し、そのあと消します。消去（8.2）でも消します（答え 106）。
- 入り直しのときは、URL に入った管理者の公開鍵で、管理者の一覧の署名を確かめます（答え 84）。その一覧から始め、一覧に載った管理者の署名を、版の順にいちばん新しい一覧までたどって（鎖で）確かめます（答え 96）。鎖に要る一覧は、招待した管理者の EUD が入るためだけの握手の返事に入れて送ります。招待を消すときに、この一覧も消します（答え 101）。招待の URL を作るとき、URL を作る管理者は、そのときの版の管理者の一覧に自分の署名を添えて、この一覧と一緒に残します。入る側は、URL に入った管理者の公開鍵でこの署名を確かめて最初の一覧とし、そこから鎖をたどります。その版に署名した管理者が URL を作った管理者と違っても同じにします。URL の大きさは変わりません（答え 109）。添える署名は ASCII の `DistribuTAK/anchor/v1` ‖ 一覧の payload に付け、起点は入るためだけの握手の返事（招待の URL の握手の鍵と TOTP で確かめた通信）で届いたものだけを使います（答え 146 の 10・148）。
- グループを作った管理者は、最初に空の失効の一覧に署名しておきます。入るためだけの握手の返事には、管理者の一覧の鎖と一緒に、いちばん新しい失効の一覧を入れて渡します。有効な失効の一覧を持つまで、EUD はほかのメンバーの証明書を受けません（答え 141）。
- 入り直しのたびに、管理者が新しい URL を作ります。前の URL は使いません（答え 82）。

- 起動し直したときに招待を持ち越すかは、まだ決めていません（答え 130）。第9段では持ち越さず、ATAK を起動し直すと招待は消えます（答え 163 の 4）。

### 5.2 URL と QR コード

- URL には、相手の宛先と、鍵を確かめる値を入れます（答え 17）。握手の鍵は短くせずに入れます（答え 20）。
- 待ち合わせのサーバーは置きません（答え 17）。
- 招待の URL と招待の QR コードの形は `distributak://join#<中身の base64url>` です（答え 89）。中身を `#` のあとに置くので、ブラウザに渡ってもサーバーには送られません。
- 中身は、管理者の EUD の番地、UDP の口の番号、握手の鍵（全部の長さ）、管理者の公開鍵、TOTP の秘密の値です（答え 89）。

- 中身の `.proto` は `core/src/main/proto/invitation.proto` の `Invitation`（proto3）です（答え 123）。ライブラリは `protobuf-javalite` 3.25.5 です（答え 124。references NW25）。

- 正規の形だけを受けます（答え 125）。base64url には `=` を付けず、`=` を付けたものや正規でない形は拒みます。Protocol Buffers は、項目の番号の順に並んだものだけを受け、知らない項目と重なった項目は拒みます。あとで項目を足すときは、古い版との互換の扱いを決め直します。
- 秘密の値を消せるように、招待は生成のメッセージに持たせず、項目の番号で読み書きします（答え 124）。

- DHT で見つけた相手（揮発の相手）は、ネットワークが変わったとき・セッションも握手も無いとき・証明書の検査に落ちたときに消します。鍵を 0 で埋め、経路・番地・速度の枠を消しますが、時刻の記録は残します。保存した相手の枠は、保存した相手を登録したときだけ 1 つ空けておきます（127 台と 1 台。登録が無ければ 128 台。上げる前は 31 台と 1 台）。pin が残る間は、DHT の相手とつなぎません（答え 182）。
- 線の形（答え 183）: DHT の項目（同期の包みの項目 9）は、同期の包みの版 2 だけで使います。相手が新しい版を話すかは、PING で探って確かめます。r19 の相手には、この探りの PING のほかは項目 9 を送りません。YES の相手でも、要求が続けて 3 回（仮の値）期限切れになったら分からないに戻し、上の回数の中で探り直します（答え 184 の 4）。探りは 0・60・180・420・900・1860 秒で、相手ごとに 24 時間で 12 回まで、全体で毎分 30 回までです（最初は毎分 6 回。模擬の結果で上げた。答え 192 (3)・193）。探りの回数の記録は相手の覚えとは別に持ち、相手を消しても・ネットワークが変わっても消しません（24 時間で消す。上限 1024 件）。
- STORE は、DHT を話すと分かった相手にだけ送ります。返事（STORE_RESULT）は、自分の出した STORE に合うものだけを受けます。形のおかしいもの・ほかのグループのものは、速度の枠を使う前に捨てます。FIND_NODE の続きは状態を持たずに返します。大きな物を分けて送る仕組み（Transfer）は作りますが、第12段では受けた転送の渡し先をつながず、捨てます。転送で受けた物は預かりの表にも答えにも載せません。CI では実際の UDP で 3 MiB を送る試験を 1 件行います。渡し先をつなぐのは、預かる物が発見の記録より広がるので、legal Q107 (2) と答え 181 の 6 の範囲を確かめてから別に決めます（答え 183 の 7）。転送は DHT を話すと分かった相手にだけ始めます。BLAKE2s の値が合わない転送には、全部受けたという ACK を返しません。断りの返事も速度の枠を通ってから返します（答え 184）。
- ログには、protobuf の型や中身を書きません（答え 166 (5)・183）。
- プラグインの配線（答え 196・197）: 発見の記録に署名する前に、必ず版を保存して予約します。予約できなければ出しません。入り直しの途中と、壁時計が負のときは版を取りません。配り直しは 1 時間ごとで、0〜5 分のばらつきを足します。時間は単調時計で数え、単調時計が戻ったら世代を進めます。DHT の仕事はコントローラーの作業スレッドの上だけで行い、核に新しいスレッドは作りません。ネットワークが変わったときと消去のときは、口を閉じる → DHT のメモリを捨てる → 保存を消す、の順にします。DHT のメモリを捨てるときは、経路表・揮発の相手に加えて、期限内のものも含めて預かっている記録を全部消します（例外で DHT だけ止めたときも同じ。答え 198 (5)・199）。揮発の相手で枠が埋まっているときに相手を保存すると、認証済みのパケットを最後に受けた時刻がいちばん古い揮発の相手を 1 台手放します（答え 198 (1)）。
- 画面（答え 196 (3)〜(6)）: 「DHT 経路表: N 預かり: N 検証で拒否: N」の 3 つの数と、「DHTを探し直す」のボタンを出します。ボタンは、押すたびに版を予約して署名し直し、1 つの相手に STORE → ACK → FIND_VALUE を送ります。返ってきた記録が、確かめた返事で、持ち主が自分・鍵が合う・版が今回 STORE した版と同じときだけ「DHT: 相手から自分の記録を受け取れました」と出します。ほかは「DHT: 見つかりませんでした」「DHT: DHT の相手がいません」「DHT: しばらく待ってから押してください」の決まった文です。押す間は単調時計で 60 秒あけます。logcat には数だけを出します。
- そのための核の口（答え 197）: 決まった相手 1 台に 1 回だけ FIND_VALUE を送る `findValueFrom`、STORE の受理（ACCEPTED・DUPLICATE）を true で返す `store(…, Consumer<Boolean>)` を足しました。どちらも結果は 1 回だけ渡し、待ちを捨てたときは null で 1 回渡します。ボタンの結果と配り直し（DhtPublisher）の結果は混ぜません。ボタンで受け取った記録は預かりの表に入れません。大きな転送で来た VALUE は、第12段では「見つかりませんでした」と扱います。
- 第13段（4.5）: 768 バイトを超える管理の記録（署名つきで 3 MiB まで）は、この Transfer で運びます。管理用の型だけを受ける渡し先をつなぎ、全体の署名を確かめてから一度だけ当てます。途中まで受けたものは当てません（ADR 0030 の答え 203 の 4）。

第8段（PRC-21.16）で、外の網で受ける前の備えを作りました。正本は ADR 0030 の答え 160 です。試験は PC のループバックだけで、値はどれも PC での試しの値です。外の網・Android の試験の前に見直します。

- **番地を確かめるクッキー**: `DTK` の 1 通目と、登録した招待への `DTJ` の頼みには、いつもクッキーを求めます。受ける側は新しい外枠 `DTC` 版 1 の CHALLENGE（80 バイト。1 通目のハッシュとクッキー）を送り元へ返し、送る側はクッキーと元の 1 通目を PROOF で包んで送り直します。クッキーは今ある HMAC-SHA256 で作り、30 秒未満だけ使えます。秘密は口ごとに持ち、60 秒で交代します（答え 160 の 1〜3・6）。
- **線の形**: `DTK` 版 1・`DTJ` 版 1 の線の形は変えません。PROOF の中身は 1184 バイト以下で、パケットは 1232 バイト以下です（答え 160 の 3）。
- **数の上限**: CHALLENGE を出す枠、MAC を確かめる枠、クッキーが正しかった包みだけが使う握手の枠の 3 段で数えます。握手の計算・HPKE・provider は、クッキーが正しく枠を通ったあとだけです。送り元ごとの記録は、クッキーが正しかった送り元にだけ作ります（答え 160 の 4・5）。
- **返事を送る相手**: 登録していない相手に握手の返事は送りません。状態を作らない CHALLENGE だけは包みの送り元へ返します（答え 158 の 4 を答え 160 の 7 で書き分けました）。第12段からは、DHT で見つけた相手でも、クッキーの PROOF と証明書の全部の検査（管理者の署名・失効・期限・握手の鍵の一致・身元の署名）を通った同じグループのメンバーには 2 通目を返します。それ以外には返しません。保存した相手の発行の順の検査は残します（答え 181 の 5）。
- **`refresh` の重さ**: 証明書と 2 つの一覧が同じオブジェクトの間だけ、Ed25519 の署名の検査結果を使い回します。失効・期限・時刻の幅は毎回確かめます（答え 160 の 8）。
- **閉じた合図**: 口が閉じたとき、理由を上の層の受け口に 1 回だけ知らせます（答え 160 の 9）。
- **残る危険**: でたらめな包みを毎秒 512 通より多く送られると、その間は新しい握手が通りにくくなります（答え 160 の 12）。

### 6.3 回線

- 回線ごとに、プラグインのソケットを Android の `Network` に結びつけます（`Network.bindSocket`。答え 43。NW12）。ソケットは、つなぐ前に結びつけます（NW12）。

### 6.4 仮想の網の番地

- 番地は、端末の ID から IPv6 のユニークローカルアドレス（`fd00::/8`）を作ります（答え 58。NW15）。
- 割り当てる役は置きません（答え 58）。
- 番地は、`fd` に端末の ID（2 章）の頭の 120 ビットを続けたものです（答え 70。NW15）。65536 台でも、番地が重なるおそれは無視できるほど小さいとしています（答え 70）。

### 6.5 時刻

- 時刻は、EUD の時計（携帯網か GNSS で合わせたもの）を使います（答え 46）。
- 握手のときに測った相手との時刻の差は、画面に出すだけにします。差が大きいときは「時計を合わせて」と出します（答え 46・85）。
- 招待の 24 時間と、同じ返事を返す 10 秒（5.1）は、EUD の時計ではなく単調な時計で数えます（答え 130）。TOTP の値の計算だけは EUD の時計を使います。
- 自分の EUD の時計で比べるのは、期限（stale の時刻・証明書の期限・削除の印の期限）だけです。相手の言う時刻で期限が延びないようにするためです（答え 85・98）。ただし、次の項の版の時刻の上限だけは、自分の時計に対して判定します（答え 105）。
- CoT の版は、その CoT を作った EUD の時刻と、その EUD の ID です。版の順はこれで決めます（答え 42・98。7 章）。受ける EUD は、自分の時計より先すぎる版の時刻と、長すぎる stale の時刻に上限を付けます。上限を超えたものは断ります（答え 111）。上限は、版の時刻が自分の時計の 5 分先まで、stale の時刻が自分の時計の 30 日先までです（答え 105・112・122）。

- **受けた CoT を ATAK に入れるとき（柵）**（答え 168 (1)）: 受けた uid と送信禁止の記録を保存してから入れます。入れる口は `getInternalDispatcher()` だけです。`PreSendProcessor2` で、受けた uid の CoT（その uid を対象にする削除のイベントも含む）だけを CONSUMED にします。送り先の種類 `TAK_SERVER`・`POINT_TO_POINT`・`ANY` のすべてで確かめます。`nevercot` は補助です。登録を失ったことに気づければ同期を止めます。気づく公開の口がなければ、いつも気づけるとは言えません。奪い返しは繰り返しません。知らないプラグインや登録の取り合いがあって柵が両立すると確かめられないときは、ATAK に入れません。
- **ATAK への取り込みは、実機の確かめが通るまで有効にしません**（答え 168 (1)）: (i) `getInternalDispatcher()` で入れた試験の物が、標準のメッシュと TAK サーバーへ出ないこと、(ii) `PreSendProcessor2` の登録と CONSUMED が SDK 5.8.0.9 で働くこと。確かめは利用者の 2 台・家の Wi-Fi・架空の試験のデータだけで行い、利用者が用意した観測先で見ます。
- **止められない経路（制約）**（答え 168 (1)(2)。ADR 0025 と同じ扱い）: ATAK の自動の送り直し・編集のあとの送り出し・手での共有と書き出し・削除の放送・起動してからプラグインが柵を戻すまでの間・ほかのプラグインとの `PreSendProcessor2` の登録の取り合い・停止や消去や取り外しのあとに地図に残る物・利用者が設定した TAK サーバー（ATAK の中の部品やほかのプラグインが `CommsMapComponent.sendCoTToServersOnly` を直接呼ぶと、柵を通らずにそのまま出ます。答え 171）・プラグインの無い受け手や画面のキャプチャ。柵はこれらを止めきれません。同意の文に書きます（`02-functional-spec.md` の 6.2）。

## 8. 鍵の写しと消去

### 8.1 管理者の鍵の写し

- 写すのは管理者の鍵です。身元の鍵は出ません（答え 71）。
- 管理者がはっきり操作したときだけ、QR コードで取り出します。パスフレーズでは包みません（答え 30・31）。
- 戻すときは、別の端末の画面に出した QR コードを、プラグインのカメラで読み取ります。画像のファイルから読み込む口は持ちません（答え 34）。
- 1Password への保存は、利用者が手で行います（答え 32）。
- QR コードは、出してから 60 秒で自動で消します。もう一度出すには、改めて操作します（答え 79）。
- 管理者の鍵の写しの QR コードは、中身が秘密の鍵そのもの（答え 31）なので、招待の URL と同じ扱い（5.2。秘密の値を伏せる・クリップボードを消す・履歴に残さない・対面か相手を確かめられる経路だけで渡す）にします。すでにいるメンバーを見つける QR コードには当てません（答え 107）。
- 画面には「1Password」の名前を出さず、「パスワードの管理アプリ」のように書きます。この文書の説明では、これまでどおり 1Password と書きます。下の注意は画面に出す文なので、「パスワードの管理アプリ」と書きます（答え 83）。

QR コードを出す画面には、次の注意を出します。ADR 0030 の答え 30〜32 のあとに書いた注意で、決定ではありません（`02-functional-spec.md` の 8.1）。注意として出すもので、プラグインが止める機能ではありません。

- 画面に出している間は、人に見せない。
- 画面を写したときは、写した画像が Android のギャラリーと、写真のクラウドのバックアップに残りうる。パスワードの管理アプリに添付したら、端末とクラウドの両方から消す。
- 中身の文字列をパスワードの管理アプリに貼るときは、クリップボードに残りうる。


### 8.2 消去

- プラグインの「消去」の操作と、自分の失効を受けたときに、鍵とデータを消します（答え 46）。
- 消去では、Keystore の鍵を消します。包んだ鍵は、それで開けなくなります（答え 73）。
- 鍵のほかに、プラグインが持つもの全部（同期の記録、DHT の記録、削除の印、相手の一覧）を消します（答え 80）。ATAK の地図に出ている CoT は、ATAK の操作で消します。プラグインは消しません（答え 80）。
- 同期の記録のファイル `sync.bin` と、その一時ファイル（`.bak`・`.new`）も消します。初回の立ち直り（`initial.pending`）でも消します（答え 168 (6)）。
- DistribuTAK から受けて地図に入れた CoT も、消去と停止のあとに地図に残ります（答え 80・168 (2)）。受けた uid の記録と柵も消えるので、残った物は ATAK の標準の経路で外へ出ることがあります（制約。7 章）。
- 加入の確定やグループ作りが途中で止まったら、次の起動で止まる前の状態に戻ります（消去済みの端末なら消去済みのまま）。入り直し・作り直しはやり直します（答え 168 (8)）。
- 手で消去するときは、先にすべてのセッションを閉じ、つなぎ直しと待ち受けを止めてから消します。消したあとは、入り直すまでどこにもつなぎません。相手には知らせません（答え 99）。
- 消したあとは、利用者が新しい招待の URL か QR コードを読んで加入するか、新しいグループを作るまで、待ち受けもつなぎ直しもしません（答え 103・164）。
- 消したあとに作るグループは、元のグループとは別のグループです。グループの ID・管理者の鍵・グループの鍵・TOTP の秘密・端末の身元の鍵と握手の鍵・ポートをすべて新しく作ります。新しいグループの状態を包んで保存できたら「消去済み」の印を消します（答え 164）。
- 自分の失効を受けて消すときも、手で消すときと同じ順で消します（答え 104）。
- 消す順は、止める → Keystore の鍵を消す → ファイル・一時ファイル・相手・メモリを消す、です。メモリの中の鍵は、使い終わった配列を 0 で埋めます。String・Bitmap・暗号のライブラリの中の写しと、フラッシュの上書きは保証しません（答え 163 の 3）。

- 受けた管理の記録の履歴は、この段では縮めません（ADR 0030 の「まだ決まっていないこと」）。かわりに、`state.bin` の包み（上限 1 MiB）が 512 KiB を超えたら、ログ（固定の文字列）と画面で知らせます。
