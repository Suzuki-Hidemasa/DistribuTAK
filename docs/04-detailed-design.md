# DistribuTAK の詳細設計

ADR 0030（`PRC-163:docs/decisions/0030-device-as-lan-router.md`）で決まった値と方式だけを書きます。部品の分け方とデータの流れは `03-basic-design.md` にあります。

決まっていない値は、推測で埋めずに 9 章の要確認の表に書きます。そこにある値は、利用者に確かめ、答えを先に ADR 0030 に書いてから、この文書に書き足します。

## 1. 暗号の組み合わせ

| 用途 | 方式 | 出典 | 根拠 |
|---|---|---|---|
| 握手の型 | `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s`（WireGuard と同じ） | NW1・NW2 の 5.4 節 | 答え 19・33 |
| 鍵の交換 | X25519 | CR7（RFC 7748） | 答え 20・33 |
| 暗号と改ざんの検出 | ChaCha20-Poly1305 | NW10（RFC 8439） | 答え 33 |
| ハッシュ | BLAKE2s | NW11（RFC 7693） | 答え 33 |
| 身元の鍵の署名 | Ed25519 | NW18（RFC 8032） | 答え 14・20・119 |
| 新しいグループの鍵と、入るときの証明書・グループの鍵を包む | HPKE。DHKEM(X25519, HKDF-SHA256)・HKDF-SHA256・AES-128-GCM、base モード | CR7（RFC 9180） | 答え 59・60・67 |
| 管理者の鍵の署名 | Ed25519（身元の鍵とは別の鍵） | NW18（RFC 8032） | 答え 71・119 |
| 鍵をしまうときに包む | Android の Keystore の取り出せない AES の鍵 | NW17 | 答え 73 |

- どれも公開標準です。実装は、よく知られたライブラリを使います（答え 11。DT-CN-02）。
- 暗号のライブラリは Bouncy Castle（Java）にまとめます（答え 72。NW16）。X25519・Ed25519・ChaCha20-Poly1305・BLAKE2s・AES-128-GCM・HKDF-SHA256・HMAC-SHA256 をここから使います。
- Noise（NW1）と HPKE（CR7）は、これらの部品から、それぞれの仕様のとおりに組み立てます。試験のベクトル（HPKE は CR6）で確かめます（答え 72）。
- Noise の試験のベクトルは、Noise の実装（cacophony、snow など）が公開しているもののうち、`Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s` のものを使います。どれを使うかと出どころは、作るときに確かめて `PRC-163:docs/references.md` に書きます（答え 78）。
- 暗号は、EUD の IP（Wi-Fi の LAN・モバイル回線）の上だけで使います。`AMATEUR` の電波区間には出しません（答え 11。DT-CN-01）。
- Ed25519・SHA-256・HMAC・AES-GCM・HKDF の出典は、references の NW18〜NW22 に足しました（答え 119）。NW3〜NW5 は欠番のままです。

## 2. 鍵

| 鍵 | 方式 | 持つもの | 根拠 |
|---|---|---|---|
| 身元の鍵 | Ed25519 | 端末ごとに 1 つ。端末の ID のもとになる | 答え 20・46 |
| 握手の鍵 | X25519 | 端末ごとに 1 つ。身元の鍵で署名する。作り直しても身元は変わらない | 答え 20 |
| グループの鍵 | 握手の psk | グループごとに 1 つ。メンバーを外したら作り直す | 答え 21・59 |
| 管理者の鍵 | Ed25519（身元の鍵とは別） | 管理者ごとに 1 つ。証明書・失効の一覧・管理者の一覧に署名する。公開鍵は管理者の一覧に載せる | 答え 22・28・71 |

- URL と QR コードには、相手の握手の鍵を短くせずにそのまま入れます（答え 20）。
- 端末の ID は、身元の鍵（Ed25519）の公開鍵の BLAKE2s-256 です（答え 46・70。NW11）。
- 身元の鍵・握手の鍵・グループの鍵・管理者の鍵は、Android の Keystore の中の取り出せない AES の鍵 1 つで包んでから、プラグインの保存場所にしまいます（答え 73。NW17）。Ed25519・X25519 を Keystore に直接しまえない端末でも動きます。
- 包む鍵は Keystore の AES-256-GCM（タグ 128 ビット。IV は Keystore が作る）です。利用者の認証と StrongBox は求めません。ATAK を起動し直したときに読み戻せるようにするためです（答え 163 の 1）。そのため、ハードウェアで守るとは画面にもドキュメントにも書きません。
- 保存の場所は、ホストの application Context の `getNoBackupFilesDir()/distributak/` です。ATAK の UID の内部の領域で、ATAK の中のほかのコードからは隔てられません（答え 163 の 2）。招待・TOTP の秘密の値・URL・セッションの鍵・クッキーはしまいません（答え 163 の 1）。開けないときは止めて、自動で作り直しません（答え 163 の 2）。加入した側は、最初の握手が終わるまで、招待にあった管理者の握手の公開鍵と番地（どちらも公開の値）を包んだ状態に入れ、口を開き直すときに pin を作り直します。最初の握手で相手の証明書と番地を保存できたら、この記録は消します。加入が確定しなかったときの保存は残しません（答え 163 の 11）。

## 3. 握手

### 3.1 1 通目

- 1 通目には、時刻の値と自分の証明書のほかは入れません。CoT などの中身は、握手が終わってから送ります（答え 19）。
- 時刻の値は、WireGuard と同じ TAI64N の形にし、暗号の中に入れます（答え 19。NW2 の 5.1 節）。
- 受ける側は、相手ごとに、受けた中でいちばん新しい時刻の値を覚えます。その値以下の 1 通目は捨てます（答え 19）。
- 時刻の値は、相手ごとに増えていれば受けます。自分の時計との差に上限は付けません（答え 53）。
- 受ける側は、1 通目の中の証明書を確かめ、グループの外の EUD を弾きます（答え 21・22）。確かめる中身は 4.1 にあります。
- 1 通目の中身（Noise のペイロード）は、TAI64N の時刻の値（12 バイト）のあとに証明書のバイト列を続けたものです（答え 128）。
- 時刻の記録は、いまの核（PRC-21.8）では証明書を確かめる前に確定します。証明書を確かめてから確定する形と、記録の数の上限（または相手ごとに消すこと）は、証明書を作る段で足します（ADR 0030 の「まだ決まっていないこと」）。

### 3.2 2 通目

- 2 通目の終わりで、グループの鍵（psk）が混ざります（答え 21。NW1 の 9.4 節）。グループの鍵を持たない EUD は、握手を終えられず、中身を復号できません。
- 受ける側は、2 通目に自分の証明書を入れます。形は 1 通目と同じです。握手を始めた側は、その証明書を 4.1 の 5 つで確かめてから、CoT などを送ります（答え 102）。
- 握手のときに、相手との時刻の差を測ります（答え 46）。測った差の使い方は 6 章にあります。
- 2 通目の中身も、1 通目と同じく TAI64N の時刻の値（12 バイト）のあとに証明書のバイト列を続けたものです。2 通目の時刻は、時刻の差を測るだけに使い、時刻の記録（3.1）には使いません（答え 128）。
- 1 通目・2 通目を読むのに失敗したら、その握手は閉じ、握手の状態を消します（答え 131。NW1 の 5 章）。

### 3.3 握手のあと

握手が済んだあとの相手ごとの鍵は、WireGuard の値で作り直します（答え 74。NW2）。値は資料で照らし合わせていません。

| 項目 | 値 |
|---|---|
| 握手し直す | 2 分たったら |
| 使わない鍵 | 3 分より古い鍵 |
| 作り直す送った数 | 2^60 通 |
| 受けない送った数 | 2^64 − 2^13 − 1 通を超えたら（ちょうどの値までは使う。答え 131） |

握手のあとの通信は、読めなかったもの（改ざんなど）を捨てて続けます。捨てたもので番号や鍵は変わりません（答え 131）。

相手が失効の一覧に載ったとき、相手の鍵が新しい鍵に変わったとき、相手の証明書の期限が切れたときは、その相手とのセッションをすぐに閉じます（答え 81）。「新しい鍵」は、証明書に入っている握手の鍵だけです。上の表の作り直す鍵（相手ごとに 2 分おき。答え 74）と、グループの鍵の作り直しは、すぐに閉じる条件には入れません（答え 95）。グループの鍵を作り直したときは、残るメンバーと新しい鍵で握手し直します（4.3。答え 81）。新しい鍵での握手が済んだ相手から、古い鍵で張ったセッションを閉じます。済むまでは古いセッションを使い続けますが、使える時間に上限を置き、過ぎたら閉じます。上限は 180 秒です（答え 108・110）。

### 3.4 メンバーどうしのセッションの細目

第5段（PRC-21.13）で決めた細目です。正本は ADR 0030 の答え 153〜157 です。ここでは要点だけを書きます。核の中だけで作り、ソケット・送信はまだ作りません。

- **パケットの形**: 40 バイトの枠（`DTK` と版 1・種類・16 バイトのセッションの識別子・グループの鍵の版・DATA の番号）のあとに、Noise の握手のメッセージか転送の暗号文を続けます。DATA の枠全体を暗号の AAD にします（答え 153 の 1）。
- **番号の窓**: 受けた最大の番号と、その手前 2048 個ぶんを覚えます。認証が通ってから窓を進めます（答え 153 の 2）。
- **大きさ**: 1 つのパケットは 1232 バイトまで、DATA の平文は 1176 バイトまでです。超える平文は、分割を作るまで送らずに断ります（答え 153 の 3・155）。分割は CoT の同期の段（第10段）で作ります（答え 166 (3)）。
- **送り直し**: 1 つの試み（送ると決めてから 90 秒）のあいだ、1 通目は 5 秒に 1 通まで（最大 18 通）です。2 通目を確かめられずに握手を作り直しても、試みの開始時刻と間隔を引き継ぎます。90 秒であきらめ、次に送るときに核が新しい握手を始めます。送れなかった中身は預かりません（答え 153 の 4・12・14、答え 154）。
- **受けた側の完了**: 受けた側は、始めた側から新しい鍵で認証の通ったパケット（始めた側が送る空の DATA）を初めて受けたときに切り替えます（答え 153 の 5）。
- **同時に始めたとき・張れたあとの新しい 1 通目**: 握手中なら公開鍵の小さい側の握手を残します。張れたあとに届いた新しい 1 通目は、証明書と時刻の記録が通れば未確認の候補で答え、確認が来るまで張れたセッションを残します。1 つの 1 通目への 2 通目は 18 通までです（答え 153 の 6）。
- **古い鍵と新しい鍵**: 相手ごとに、張ったセッション 1 つと候補 1 つまでです。切り替えたら古い鍵はすぐ 0 で埋め、遅れて届いた古い鍵のパケットは捨てます（答え 153 の 7・156）。
- **時計と呼び出し**: 核はタイマーのスレッドを持たず、呼び出し元が `refresh` と `poll` を呼びます。5 秒・90 秒・2 分・3 分・180 秒は単調な時計で比べます（答え 153 の 8）。時計を戻した直後の時計の差のずれは受け入れ、表示は目安にします（答え 153 の 9・157）。
- **証明書の発行の順**: 覚えている証明書より発行の古い証明書は断ります。このため、新しい証明書を先に覚えた側は、相手が新しい証明書を覚えるまで、前の証明書を出す相手と握手しません（答え 153 の 11）。
- **グループの鍵を作り直したとき**: 張れたセッションを持つ相手と、握手中・確認待ちの相手だけと新しい版で握手し直します。一度も握手していない相手・90 秒であきらめた相手・セッションを失った相手・失効した相手とは、次に送るときに握手します。確認待ちの候補しかなかった相手には、作り直しの時点から自分の新しい試みを始めます（90 秒はそこから数え、続けて作り直しても延ばしません）。前に 90 秒であきらめた相手でも、作り直しのときに確認待ちの候補を持っていれば予定に入れます（答え 153 の 13）。
- **数の上限**: 覚える相手はグループの台数の上限 −1 台まで、セッションと握手の状態は合わせてその 2 倍までです（答え 153 の 10）。
- **残る制約**（第5段の再レビューの申し送り。DoS 対策のクッキーなどのあとの段で見直します）:
  1. 相手が 90 秒であきらめた本物の 1 通目が遅れて届くと、受けた側は候補を作り、候補が 90 秒で消えるまで自分から握手を始められません。候補が消えたあとに送ろうとすれば新しい握手を始めます。相手から新しい 1 通目が来ればすぐ回復します。同じ 1 通目で起こせるのは 1 回だけです。
  2. 相手の記録に自分の 1 通目の時刻が残っているときに時計を戻して起動し直すと、記録より新しい時刻になるまで握手が通りません（1 通目の時刻の記録の規則。3.2）。戻した幅が経過した時間より大きいと、そのぶん長く通りません。
  3. 確認の DATA が失われ、そのうえ相手が起動し直したときは、候補だけを持つ側は最大 90 秒、自分から握手を始められません。相手から新しい 1 通目が来ればすぐ回復します。

### 3.5 UDP の口

第6段（PRC-21.14）で、3.4 のセッションを 1 つの UDP の口に載せました。正本は ADR 0030 の答え 158 です。ここでは要点だけを書きます。試験は PC のループバック（127.0.0.1 と ::1）だけで行い、外の網・実機・無線は使っていません。

- **受ける形**: 65535 バイトの入れ物で受けて長さを見て、1232 バイトを超えるものは切り詰めずに捨てます。`DTK` 版 1 の枠でないもの・短いものは、暗号の処理の前に捨てます（答え 158 の 1）。
- **スレッド**: 受けるスレッド 1 本と、250 ミリ秒おきに `refresh`・`poll` を呼ぶ時計のスレッド 1 本です。届いた平文は核のロックの外で受け口（コールバック）に渡し、戻ったら 0 で埋めます。受け口が戻らないと `close` も戻りません（答え 158 の 2）。
- **閉じ方**: 呼び出し元の `close` のほか、自分の証明書が失効・期限切れになって核が閉じたとき、受けるソケットが壊れたとき、時計の処理が壊れたときも、口は自分で閉じます（ソケットとスレッドを止め、鍵を 0 で埋める）。閉じたあとの `send` は false を返します。閉じた理由は照会で分かります。上の層に知らせる合図はあとの段で決めます（答え 158 の 3）。
- **相手の番地**: 認証と番号の窓を通った新しい DATA でだけ、相手の番地を変えます。1 通目・2 通目・改ざんしたもの・重ねて届いたものでは変えません。DATA の前に相手の番地が変わったときは、上の層が番地を覚え直します（答え 158 の 4）。
- **管理の一覧**: 管理者の一覧・失効の一覧の採用と `refresh` を同じロックの中で順に行います。口には、`SessionManager` を作ったときと同じ管理の状態を渡します（答え 158 の 5）。
- **送り直さない**: 届いた中身は受け口に渡すだけで、ほかの相手へ送る道はありません。A から B への中身が C に届かないことを試験で確かめています（答え 158 の 7。legal Q107 (2)）。
- **重さ**: 50 台の相手で `refresh`・送る・受けるの平均は約 4.8 ミリ秒でした（PC で測った値。Android では測っていない。答え 158 の 8）。
- **DoS 対策のクッキー**: 第8段で作りました（答え 160。下の段落）。

第7段（PRC-21.15）で、入るためだけの握手（4.4）も同じ口に載せました。正本は ADR 0030 の答え 159 です。試験はやはり PC のループバックだけです。

- **見分け方**: 入る握手は別の頭 `DTJ` の版 1 で送ります。見出しは 64 バイト、断片の中身は 1168 バイトで、パケットは 1232 バイト以下です。`DTK` の版 1 は上のとおりに処理し、知らない頭は捨てます。求め（最大 433 バイト）は 1 つのパケットに収まります（答え 159 の 1）。
- **返事の送り方**: 管理者は求めに 64 バイトの READY だけを返し、入る側が番号で取りに行く FETCH 1 通につき返事の断片を 1 通返します。送る量が受けた量を超えないので、偽の送り元の番地で他人に大量に送らせることはできません。最初の求めの番地に固定し、速度にも上限を置きます（答え 159 の 2）。
- **確かめ方**: 断片ごとには確かめず、組み立てたあとに HPKE と署名で全体を確かめます。壊れていたら 2 回まで全体を取り直します（答え 159 の 3）。
- **時間**: 返事を 10 秒持つこと（答え 113）、1 秒おきに 5 回まで送り直すこと（答え 150 の 8）は変えていません（答え 159 の 4）。
- **秘密**: 口は管理者の秘密を持ち続けず、求めのたびに呼び出し元から受け取り、使い終わったら 0 で埋めます。重い処理は別のスレッドで行い、メンバーどうしの受信を止めません（答え 159 の 7）。
- **入ったあと**: 入る側は、同じソケット・同じ番号のまま、メンバーどうしのセッションに移ります（答え 159 の 8）。管理者の側の呼び出し元には、出した証明書と新しいメンバーの公開鍵を渡します。一覧に載せて配るのは呼び出し元の仕事です（答え 159 の 9）。
- **送り直さない**: 届いた入るための求め・返事と握手の求め・返事を、ほかの相手へ送り直したり預かったりしません（答え 159 の 10。legal Q107 (2)）。DHT の記録は別で、5.3 の範囲で預かります（答え 181 の 6）。
- **残る課題**: 16 MiB に近い返事は、外の網では 10 秒に収まらない見込みです。偽の断片を差し込み続ける相手への備えも含めて、外の網の段で見直します（ADR 0030「第7段のあとの段で決めること」）。

## 4. 証明書と管理の記録

### 4.1 証明書

| 項目 | 値 | 根拠 |
|---|---|---|
| 署名する人 | 管理者の一覧に載った管理者 | 答え 22・28 |
| 中身 | メンバーの身元の鍵と握手の鍵、身元の鍵で握手の鍵に付けた署名、期限 | 答え 22・97 |
| 期限 | 30 日 | 答え 24 |
| 更新を始めるとき | 残りが 3 分の 1 ほど（10 日ほど）になったとき。管理者に届くときに自動で行う | 答え 24 |
| 管理者に 30 日届かなかったとき | 期限が切れ、グループのほかの EUD とつながらなくなる | 答え 24 |
| 画面に出すもの | 自分の証明書の残りの日数と、自動の更新の回数だけ。期限の時刻・鍵の値は出さない | 答え 178 (3) |
| 実機での更新の確かめ | 試験のグループ（2026-11-13 に作り直した）の更新が始まる 2026-12-03 ごろに行う。期限を短くする・しきい値を下げる切り替えは作らず、核の試験は差し替えた時計で確かめる | 答え 178 (4) |

握手の 1 通目を受けた側と、2 通目を受けた始めた側は、証明書について次の 5 つを確かめます（答え 22・28・84・85・97・102）。

1. 管理者の一覧に載った管理者が署名している。
2. 失効の一覧に載っていない。
3. 期限の中にある。期限は、自分の EUD の時計で比べる（答え 85・98）。発行の時刻が自分の時計より先でも 5 分までなら受けます。期限の終わりには余裕を付けません（答え 143）。
4. 相手の握手の鍵が、証明書に入っている握手の鍵と同じ（答え 84）。

### 4.4 入り直しの手順

- 新しいメンバー、新しいグループの鍵を受け取れなかったメンバー、証明書の期限が切れた EUD は、TOTP の URL（または QR コード）で管理者の EUD へ直接つなぎます（答え 60〜62）。
- URL の TOTP の値で「入るためだけの握手」をします。TOTP の値が正しければ、管理者の EUD は自動で（答え 149）、証明書とグループの鍵を、入る側の握手の鍵に向けて HPKE（4.3 と同じ組み合わせ）で包んで送ります（答え 60・67）。
- 「入るためだけの握手」のメッセージも Protocol Buffers で並べます（答え 88）。項目と細目は答え 150 で決めました（`core/src/main/proto/join.proto`）。求めは URL の握手の鍵へ、返事は入る側の握手の鍵へ、どちらも HPKE base で包みます（Noise の握手は使いません）。求めには、招待の秘密から作った鍵の HMAC（秘密を知っている証明）と TOTP を入れます。返事は URL の管理者が招待と求めに結び付けて署名し、起点からの管理者の一覧の鎖・いちばん新しい失効の一覧・証明書・包んだグループの鍵を入れます。前方秘匿はありません（答え 151 で受け入れた）。鎖は 64 件、返事は 16 MiB までです（答え 152）。
- 入るためだけの握手は、1 秒おきに 5 回まで送り直します（答え 87。仮の値で、試験で直します）。
- 管理者は、同じ求め（同じ鍵、同じ TOTP の値）の送り直しには、短い時間のあいだ、同じ返事をもう一度返します。別の鍵からの求めは断ります。同じ返事を返す時間は 10 秒です（答え 93・113）。これは新しく入る求めを受けることではなく、前に出した返事をもう一度返すことなので、TOTP の値を 2 度目に受けることには入りません（5.1）。同じ返事を返すために、管理者の EUD は、入る側の鍵、使った TOTP の値、出した返事を、同じ返事を返す時間のあいだだけ残し、そのあと消します。消去（8.2）でも消します（答え 106）。
- 入り直しのときは、URL に入った管理者の公開鍵で、管理者の一覧の署名を確かめます（答え 84）。その一覧から始め、一覧に載った管理者の署名を、版の順にいちばん新しい一覧までたどって（鎖で）確かめます（答え 96）。鎖に要る一覧は、招待した管理者の EUD が入るためだけの握手の返事に入れて送ります。招待を消すときに、この一覧も消します（答え 101）。招待の URL を作るとき、URL を作る管理者は、そのときの版の管理者の一覧に自分の署名を添えて、この一覧と一緒に残します。入る側は、URL に入った管理者の公開鍵でこの署名を確かめて最初の一覧とし、そこから鎖をたどります。その版に署名した管理者が URL を作った管理者と違っても同じにします。URL の大きさは変わりません（答え 109）。添える署名は ASCII の `DistribuTAK/anchor/v1` ‖ 一覧の payload に付け、起点は入るためだけの握手の返事（招待の URL の握手の鍵と TOTP で確かめた通信）で届いたものだけを使います（答え 146 の 10・148）。
- グループを作った管理者は、最初に空の失効の一覧に署名しておきます。入るためだけの握手の返事には、管理者の一覧の鎖と一緒に、いちばん新しい失効の一覧を入れて渡します。有効な失効の一覧を持つまで、EUD はほかのメンバーの証明書を受けません（答え 141）。
- 入り直しのたびに、管理者が新しい URL を作ります。前の URL は使いません（答え 82）。

- **最後の通知の核（第5回の手順 4）**: `FinalManagementNotice` は署名の正しい同じグループの REVOCATIONS の内側 SignedRecord だけをページにします。外側 DHT 記録、告知・包み・名簿・CoT を渡す口はありません。専用の送信口と破棄コールバックを受け、核には送信鍵を渡しません。同じスレッドから呼びます。所有側は poll を定期的に呼び、通知の予約を作った時点（自分の候補では保存・公開のあと、受信失効では暫定拒否前）から 1 秒（または前に確かめた時刻より時計が戻ったとき）で枠とページを捨て、送信口の close を 1 回だけ呼びます。送信口の所有側は close で送信鍵を破棄します。
  - 最大長整数の内側は S=190+34n です。実際のページ数だけを相手と全体の予算で一括予約し、足りなければ全く送りません。1〜3 ページなら必要な 1〜3 通分だけを数えます。114 件は 4066 B・4 ページで、両方に 4 通分が残るときだけ送ります。115 件は 4100 B・5 ページなので送りません。予算不足なら一部だけ送らず、未完とします。ACK・再送は行わず、受信はすべて捨てます。SENT は送信口が送り出せたという結果だけで、相手の受信・一覧の完成・自動消去・理由の認識を保証しません。欠落や送信失敗は未完となり得ます。手元の失効適用と通常通信の切断は、この結果を待たせません。

- **管理ページのセッションと残件（第8b-1回）**: `SessionManager` が確立済みセッションを閉じる・交換するとき、共通assemblerの `forget(peer)` を呼んで予約・完了・破棄記録を解放します。共通senderもpoll時と再投入時に古いセッション・世代を外し、close時に残るページを消去します。通常の失効送信と復旧要求の操作番号は、通信寿命ごとの乱数8 Bと共通の単調カウンター8 Bで発行し、カウンターが尽きたら再利用せず断ります。同じ要求の再送は元の番号のままです。第8b-3回では、受信失効の暫定拒否前と、自分の失効候補の保存・公開後に、旧セッション・世代・共通発行元から一度発行した操作番号・正確な失効本体・開始時刻を固定します。maySendFinalNoticeはこの番号も照合し、別番号で同じ本体を送ることを認めません。専用送信口は未接続です。NoiseTransportが送受信の状態を一体で持つため、専用口へ送信状態を移す方法が未決です。後の段で分離を設計します。管理ページ・復旧・再送は通信を開く時に作る1個の `MonotonicClock` を共有し、署名と証明書の期限は別の壁時計で検査します。
- **管理用の DHT 記録の外側（第4回の最初の区切り。DTAK-9）**: 管理の記録は種類 2〜6 の DHT 記録（`ManagedDhtRecord`）で運びます。種類は 2＝最新の管理者の一覧、3＝最新の失効の一覧、4＝受け手あての包んだ鍵、5＝版ごとの管理者の一覧、6＝最新の鍵の告知です。記録鍵は `DhtKeys.derive` で求め、種類 2・3・6 の宛先は 32 バイトの 0 だけを受けます。種類 5 の宛先は、固定の前置き `DistribuTAK/admin-history/v1` と版（8 バイトの大きい順）の BLAKE2s です。種類 4 の宛先は受け手の識別子で、内側の項目 0 と一致させます。
  - **形式 1 は使いません（利用者の決定。2026-11-16）**: 管理用の DHT 記録の内側の一覧（管理者・失効）と種類 4 の包みは形式 2 だけを受け、形式 1 は外側の署名が正しくても断ります。版 5 の保存と第2回の更新の読み込みが使う形式 1 の扱い（`AdminState`・`AdminRecords.decode`）と、既存の LAN の鍵配布の経路は変えません。
  - 外側は payload(1)・signature(2) で、署名の用途は `DHT_MANAGEMENT`、署名は payload 全体にかけます。payload の項目は 1〜14 を決まった順に並べ、0 も書きます（schema・purpose・group・kind・record_key・signer・version・signed_at・expires_at・subject・record・publication_seq・admin_version・admin_digest）。項目 15（受け手の証明書）は種類 4 だけにあり、種類 4 では必須で 1〜1024 バイトです。受けた payload を読み直して正規のバイト列と比べ、違えば断ります。expires_at は signed_at の 24 時間後と決まっています。
  - 検査の順は、長さ→構文と正規形→宛先と記録鍵→外側の署名→内側の記録（種類・グループ・版・宛先の一致）です。構造の検査（`ManagedDhtRecord.verifyStructure`）に違反したときは、理由は `INVALID` の 1 種類だけを返し、受けた内容は例外に書きません。権限・版・競合は、構造の検査のあとに `ManagedVerifier` が判定します（次の項）。
  - **権限・版・競合の判定（第4回。DTAK-9）**: `ManagedVerifier.judge(候補, 手元の記録)` は、信頼済みの管理者一覧の鎖（`TrustedAdmins`。`AdminState` を読むだけの `AdminStateTrust`）と時計に照らして FIND の値を判定します。STORE は `judgeStore(候補, 手元の記録, 認証済みの身元)` を使い、署名者の検証済みの BOUND の対応とセッションの身元も一致させます。FIND の返答者は署名者でなくても構いません。状態・名簿・保存は動かしません。答えは `ManagedVerdict` で、STORE の答えに出すのは ACCEPTED・DUPLICATE・OLD・INVALID（`DhtWire.StoreStatus`）、NEEDS_VERSION（先に取りたい管理者一覧の版を持つ）と NEEDS_ANNOUNCEMENT は内部の保留で、通信の答えには出しません。
    - 順は、①構造と内外の署名を確かめたうえで期限（`expires_at` 以後は INVALID）と、外側・内側の署名時刻が 5 分より先なら INVALID（ちょうど 5 分は有効）→ ②足りない版（外側の `admin_version` が信頼済みの最新より先、または一覧の版が最新の次より先なら NEEDS_VERSION。最新＋1 を指す。未知の署名者でも署名自体を確かめてから保留にする。版がそろったら権限と STORE の身元を調べ直す）→ ③外側の権限 → ④種類ごとの規則 → ⑤手元の記録との順位。

    - **自己削除の例外（種類 2・5）**: 信頼済みの N から直接続く N+1 への遷移だけを受けます。外側の項目 13・14 は N の版と digest を名指しし、N の管理者 A が内側と外側の両方に署名し、空でない N+1 から A 自身が外れていることを求めます。鎖と両署名も検査します。STORE はさらに、N の A の検証済みの BOUND の対応と認証済みの身元を一致させます。採用した外側まで同じバイト列の再送は DUPLICATE とし、手元の記録と預かりの期限を変えません。外された A の別の外側での置き直し・同版の別の自己削除・欠番・過去版・別の種類・内外署名者違いは INVALID です。今の管理者による通常の欠番は、従来どおり NEEDS_VERSION にします。残る管理者による信頼済み一覧の置き直しは認めます。
    - **同版競合の勝ち直し（種類 2 だけ）**: 外された A でも、A を含む候補が最新と同じ版で順位が上なら、直前の信頼済みの版から鎖を検証し、外側がその版と digest を名指すことを条件に受けます。STORE の身元は直前版の A の BOUND の対応と照合します。この例外は種類 5 と、証明書・失効・包み・告知には広げません（ADR 0030 答え 202 の 3、提案書 3.2）。
    - 種類 2（最新の管理者の一覧）: 最新より古い版は OLD。最新と同じ中身は受け（順位へ）。最新と同じ版の別の中身は、順位が上（版→署名時刻→中身）で、直前の版から鎖でつながり、外側が直前の版を名指すときだけ受け、順位が下なら OLD、鎖か名指しが違えば INVALID。最新の次の版も、鎖と名指し（直前の版）を求め、違えば INVALID。
    - 種類 5（版ごとの一覧）: 最新より古い版は、信頼済みのその版そのものだけを受け、違えば INVALID。最新と同じ版・次の版は種類 2 と同じ規則です。

    - **同梱の受け手の証明書**: 種類 4 の外側の項目 15 で運ぶ署名済み Certificate（1 KiB 以下）を使います。グループ・今の管理者の署名・形式 2 の身元の証明・期限・発行時刻（5 分より先は拒否）・失効の和 R を検査します。`BLAKE2s(身元公開鍵)==subject==recipient_id` と、証明書の握手鍵と包みの `handshake_key` の一致を求めます。告知の失効本体に載る受け手も断ります。包みを預かっても対等の通信相手や名簿に登録せず、認証済み FIRST の検査も省きません。
    - **同じ受け手の包みの順位**: 告知の `key_version`→`signed_at`→payload、次に証明書の `issued_at`、包みの `signed_at`、包みの payload の辞書順です。同じ `issued_at` でバイト列の違う証明書は INVALID です。包みの告知 digest と告知の鍵版を一致させ、告知・失効本体がそろうまでは最新値にしません。鍵版が異なるときは、検証済みの手元の包みの版と比べ、手元の告知を求めません。同じ鍵版のときだけ手元の告知を求めます。包みを持っている間は告知も持つのが望ましいですが、保持の義務は製品へつなぐ回で決めます。外側だけの置き直しで内側の順位を覆しません。
    - **保留の上限**: `ManagedPending` は全体で 8 件・外側を符号化した合計で 4 MiB・初回から 120 秒までです。上限を超えるときは古い方を捨てず、新着を断ります。重複は（符号化したバイト列・認証済みの身元）の組で判定し、FIND の身元なしと STORE の身元ありを区別します。後着の身元で既存項目を上書きしません。件数・容量・初回からの期限は組ごとに数え、同じ組の再送で期限を延ばしません。時計が項目を入れた時刻より前に戻ったら、その項目を期限切れとして捨てます。再検査では現在の権限・失効・期限・手元の値を調べ直し、STORE の認証済みの身元も写しで保持して再照合します。retry は適用の関数を受け取り、同じ DHT 番号の候補を順位が高い方から再検査します。包みは告知が読める項目を先にし、読める同士は告知の順位（鍵版→署名時刻→payload）、読めない同士は鍵版→証明書の発行時刻→包みの署名時刻→payload で並べます。外側の署名時刻→publication_seq→符号化したバイト列で残る同順位を解きます。その通しで使う告知と証明書の発行時刻を先にそろえ、比較中は依存本体を読み直しません。
      - **身元ごとの保留枠（第8b回の決定）**: 認証済みで現在の資格を確認できる輸送の送り手ごとに2件、未知・外された署名者などの匿名入力は共通で2件です。未知のFIND署名者を枠の所有者にしません。正規メンバーが未知・外された署名者の記録を中継しても匿名枠を使います。全体8件・4 MiB・120秒と重複の元の期限を保ちます。これは、未知・外された署名者が8枠を120秒ふさぐ問題を防ぐため、利用者が決めた内部の資源上限です。保存中のSyncInboxとは対象が異なります。保持中に送り手、内側または外側の署名者が確認済みの資格を失ったら、匿名へ移さず破棄します。再検査で初めて確認できた資格も以後の喪失検査に含めます。旧offer APIは呼び出し元が認証済み身元を渡す契約を保ち、2bの入口では検証器と現在資格の検査を注入する新constructorを必須にします。
      - ACCEPTED の項目は、適用の関数を呼ぶ前に枠から外します。容量は実際に外せたときだけ 1 回引きます。関数は保存と、次の判定に必要な状態の更新を済ませてから戻ります。途中で例外を投げたら未適用として扱い、その項目を同じ初回時刻と容量で枠に戻して、同じ例外を投げます。先に適用した項目は外れたまま、未処理の項目は残ります。retry の実行中に同じ ManagedPending の公開メソッド（offer・retry・size・bytes）を呼ぶと IllegalStateException になります。
      - 更新後の手元の値で次を調べ直します。INVALID・DUPLICATE・OLD は適用せず、ACCEPTED とともに枠から外して返します。依存を待つ結果は枠に残します。1 回の通しで ACCEPTED が 1 件でも出たら、残りをもう一度通します。ACCEPTED が出なくなるか枠が空になれば終えます。ACCEPTED ごとに枠が 1 件減り、最大 8 件なので有限回で終わります。各項目の再検査前にも期限を確かめ、適用の途中で期限切れになった未処理の項目を適用しません。
  - **失効の和 R（第4回の 3 つ目の区切り。DTAK-9）**: `RevocationUnion` は、署名の検査を通った失効の一覧に載った対象を、到着順・一覧の勝者・署名者の削除によらず残します。手元の最新だけの失効（`AdminState.revocations()`）とは別に持ちます。足せるのは、グループ・署名が正しく、署名者が今の最新の管理者である失効の一覧だけで、違えば SecurityException で断ります。外された管理者の新しい失効の一覧は使いません。すでに足した対象は、署名者が外されても消しません。足すと 65,536 件を超えるときは `RevocationLimitException` で断り、和は変えず、古い失効も捨てません。`covers(一覧)` は、一覧が和のすべての対象を含むかを答えます（統合した失効の一覧や、告知が指す失効の一覧が和を欠かないことの確認に使います）。種類 4 の証明書の検査（次の区切り）はこの和を使います。
  - 大きさ: 通常の STORE に載るのは外側込みで 768 バイトまでです。`ManagedDhtRecord.transport()` は、768 バイト以下なら STORE、超えれば TRANSFER を返します。意味の判定（`ManagedVerdict`）とは分けます。失効の数値が最大のときは 7 件で 755 バイト、8 件で 789 バイトです。ふつうの数値では 8 件まで載る場合があり、1 件ごとに 34 バイト増えます。これを超える記録は、3 MiB までの Transfer で運びます。内側だけの大きさと外側込みの大きさは分けて測ります。
- **保存**: 保存は版 6 にし、管理の記録を別のファイル（上限 16 MiB）に分けます。受けた有効な失効を保存できないときは、グループの通信を止め、再起動のあとも止めたままにして、画面に「保存がいっぱい」と出します（答え 201 の 3・203 の 10）。止めた印は、版 6 に移すときに決まった大きさで作っておいたファイルへの上書きで確定させ、Keystore の鍵は消しません（答え 204 の 2）。その上書きが読み書きの故障で失敗したときは、再試行してから、そのプロセスの間だけ止めます。次の起動で止まることは保証しません（答え 205）。保存がふつうに進んでいる間は、一時の止めとして扱います。取り消していない相手とのセッションは保ち、期限（180 秒を含む）は元のまま数えて延ばしません。新しい握手・鍵の受け取り・CoT の送受信は保存が済むまで待たせます。保存に失敗したら、上の止め方に移ります（答え 206 の 2）。止めた印が残っているのに、保存した記録に失効がないときは、ふだんの通信を始める前に管理者かメンバーから失効の一覧だけを取り直します。署名と、版が印に書いた版より古くないことと、止めたときに受けた失効を含むことを確かめて保存できたら、印を消して通信を戻します。含むと確かめられないときは止めたままにし、受けた失効は捨てません（答え 209 の 4・210 の 4）。相手が見つからない間は止めたままにし、記録は自動で消しません（答え 208 の 1）。取り直す相手は、今の鍵と有効な証明書でふつうの握手が通る相手だけで、許すのは失効の一覧の要求・返事・ページの ACK だけです。古い PSK だけで取る道は作りません。グループの鍵の入れ替えが進んだあとは取り直しでは戻れないので、利用者が消去して入り直します（答え 209）。印の上書きと同期は、最初を含めて 3 回まで、100 ms の間隔で試します（答え 207 の 3）。
- **取り消す相手への最後の知らせ**: 失効を当てたら、その相手とのふだんの通信はすぐ閉じます。署名の済んだ失効の一覧のページだけを、一方向に最長 1 秒送る枠を例外として認めます（答え 204 の 3）。知らせが届ききらなかった相手には、自動の消去も、理由を知ることも保証しません。失効を当てた端末から握手を断られるだけになります（答え 207 の 4）。

第6a回では、保存中の通信を調整する `CorePersistenceCoordinator` を核に加えました。第7回で停止の印の実 I/O と保存形式 6 を加えました。限定復旧の通信は第8a回、通常失効の受信・保存・完了ACKは第8b-1回で接続しました。通常保存の一時停止は Controller から呼びます。状態と操作の判定は `SessionManager` のロックの下で行い、保存 I/O の間はそのロックと `AdminState` のロックを解放します。保存用に基準の管理状態と R の追加枠を予約し、競合する更新は待たせず断ります。断る更新には、管理者の追加・削除、失効の受理、`clear`、読み戻しが含まれ、予約の間は `IllegalStateException` になります。製品の消去や管理操作は、第8回の配線で、保存中に断られることを扱います。読み取りと期限の整理は続けます。

保存の順序は、(1) 受信失効を検証し、同じロックの下で PERSISTING に入り、対象だけを拒否して通常セッションを閉じる、(2) まだ公開しない保存候補を作る、(3) active の上書きと同期、(4) 管理記録などの保存、(5) 候補の照合と clear の同期、(6) 保存した状態を適用し、期限・世代を再検査して再開する、です。第6a回は (3)〜(5) を `PersistenceHooks` へ注入します。`AdminState` の保存用の候補は現在の状態から分け、clear が済むまで現在の状態を進めません。保存前に操作番号・世代・基準の状態と R の上限を検査します。通知候補も、R の上限を超えないと確かめてから作ります。保存のフックが戻ったあと、管理記録のストアへ保存する前にも操作番号・世代・基準を照合します。受信失効の古い完了は通常再開に使いません。

受信で知った失効は、保存前から暫定の拒否として残します。取り消した対象との通常セッションは直ちに閉じ、保存前にも新しい握手を認めません。旧セッションと同じ相手・世代に結んだ正確な失効ページだけに、最長1秒の一方向通知を認めます。送信予算と鍵の破棄は既存の `FinalManagementNotice` と専用送信口が扱い、今回の調整層は通常の送信口へ例外を足しません。非失効相手に対して `SessionManager.close` は呼びません。受信失効の保存に失敗したら STORAGE_FAILED へ移り、セッションを閉じます。自分が作った失効候補は、保存成功まで拒否側にも適用せず、保存確定前の失敗なら取り消して古い状態を保ちます。管理記録のストアへの保存が確定したあとは、途中でネットワークの世代が変わっても、予約した候補と R の追加を公開します。保存内容とメモリの失効判定を一致させ、古いセッションを復元しません。確定後の処理に失敗した場合は、保存前の状態へ戻さず STORAGE_FAILED で通信を止めます。自分の失効を保存したときは通常再開ではなく、公開後に更新予約を解放してから、既存の自動消去を呼ぶための `selfRevoked` フックへ進みます。

180秒は `rotateGroupKey` で新鍵を採用した時から、元の単調時計で数えます。失効一覧を受信しただけでは数え始めません。連続する回転でも `rotationAt` を付け直さず、保存時間も足しません。保存中に鍵を回転させる呼び出しは、鍵を適用せず拒否します。`refresh` と期限の整理は保存中も行い、180秒に達した旧セッションを閉じます。保存が成功しても閉じたセッションを戻しません。再開時にも期限と世代を確かめ直し、古い鍵による新規握手は許しません。ページの進捗30秒・全体240秒は元の期限のままです。回復開始からの240秒は、回復用の保存を始める時点で判定します。239秒で始めた保存が241秒に終わっても、検証・保存・clear が通れば採用します。240秒に達してからは新たに保存を始めません。保存や要求の再送で回復開始時刻を付け直しません。署名時刻と証明書の有効期限を調べる壁時計は別に保ち、期限の時計には `MonotonicClock` を使えます。

告知と包みは、参照する失効本体の版と署名対象の digest を照合するまで保留します。番号が合うだけでは適用しません。既存の `ManagedVerifier`・`ManagedPending` が検証と保留の共通枠（8件・4 MiB・初回から120秒）を扱います。調整層の `applyGroupKey` も保存済みの本体、今の管理者の署名と版、包みの告知 digest、宛先と握手鍵、鍵版、commitment を調べ、鍵の保存後に現在版・管理状態・期限・世代を再検査してから適用します。保存中に届いた鍵のメッセージは適用せず、調整層に無制限の待ち行列も作りません。呼び出し側は既存の有限な保留枠や再取得で補います。

受信した失効で、履歴の件数・バイト数や管理平文16 MiBの上限により候補自体を作れないときは、target_state_digest と target_R_digest をともに全ゼロとする「候補なし」のactiveを確定します。required_revocation_versionは検証済みの受信一覧の版、target_saveSeqは現在のsaveSeqです。全ゼロtargetは確定候補の証拠にならず、起動時も通常保存やclearでも停止を解除しません。履歴を削って保存を成功させず、固定文「保存がいっぱい」を保ちます。候補を作れるときは、予定digestを決めてactiveを確定したあとに空き容量を検査します。

第8a回では、有効なactiveの予定失効がstateにない場合と、全ゼロtargetの場合に限定復旧へ進みます。取り直した署名済み一覧の版がrequired_revocation_version以上で、保存済みRを包含することを要求します。全ゼロtargetを候補との一致に使いません。元のtarget全体、復旧前の署名済み履歴の接頭部分・勝者一覧・管理者版・失効版、再構成したRを新checkpointへ結びます。再起動でも署名と当時の権限を検証して旧Rを再構成し、保存した集合との一致と新一覧による包含を確かめます。証拠がなければclearへ進まず、再取得または停止を保ちます。復旧後も履歴65,536件・12 MiB、管理平文16 MiBの仮の上限を越えるなら、履歴を削らず停止を保ちます。

新鍵を含む候補の保存が未確定なら、失敗した候補を取り消し RUNNING の旧状態を保ちます。保存フックの正常終了後は確定済みとして扱い、世代・期限・基準の変更で適用できなくても旧鍵へ戻さず、補償保存もしません。全通信を STORAGE_FAILED で止め、`StopReason.COMMITTED_NOT_APPLIED` で区別します。この理由では固定文「保存がいっぱい」を出しません。受信失効の保存・印の失敗は従来どおり `StopReason.STORAGE_FAILED` で、固定文を保ちます。STALE・CANCELLED から旧状態の RUNNING へ戻れるのは保存未確定の場合だけです（第7回の S3）。

限定回復 U1 は、再起動後の新しい `SessionManager` に、起動側で検証した版の下限と停止時 R の要件を渡して始めます。旧セッションは復元しません。再構成できた停止時 R の対象は、保存済み R が空でも回復開始から失効判定に加え、握手・相手の登録・回復相手の束縛を拒否します。回復完了後は、保存した一覧を加えた通常の R で判定します。専用要求は `ManagementEnvelope` の `revocations_recovery_request=10` で、schema(1)=1、group_id(2)=32 B、operation_id(3)=16 B、required_revocation_version(4)=uint64、target_R_digest(5)=32 B をすべて明示します。未知・重複・欠落・順序違い・最短でない整数・固定長違いは断ります。封筒の番号は `cot_sync.proto` で定義し、Java の各 codec は生成定数を `ManagementEnvelopeFields` 経由で参照します。`page_ack=11` は確定の番号です。候補なしの復旧では、要求10の `target_R_digest` は全ゼロをそのまま線上に載せます。この値を通常の集合digestと照合せず、一覧を取り直す側が必要版以上であることと保存済みRの包含を検証します。

回復要求と返事は、認証済みの相手・セッション・世代・操作番号へ結び付けます。同じ要求の再送で操作や期限を作り直さず、別の操作や世代のページを混ぜません。組立は既存の相手1・全体2・予約8 MiB・進捗30秒・全体240秒の上限を使い、送り手の4/32の枠と ACK の予算も既存の管理ページの部品を使います。普通のメンバーが返すときも、受信側は一覧に署名した管理者の権限を検証します。全体の完成後に署名と版の下限を調べ、保存済み R を残し、候補が停止時 R も包含することを要求します。停止時 R を再構成できればその digest と包含を調べます。再構成できなければ候補 R の digest の完全一致だけを証拠にでき、版や件数が多いだけでは回復しません。回復から PERSISTING に移った間も、保存と clear が済むまで「保存がいっぱい」の表示を保ちます。通常の保存中にはこの表示を出しません。

相手なし、鍵の回転済み、鍵不一致、証明書期限切れ、管理者鎖の欠け、R の包含を証明できない場合、保存失敗では通常通信へ戻しません。180秒を延ばしたり、旧 PSK・期限切れ証明書の特例・平文取得で回避したりしません。自動消去や作り直しは始めず、利用者が既存の消去・入り直しを選ぶまで停止を保ちます。

新鍵の保存と告知・管理状態は `saveAcceptedKey` で一括確定します。`saveRotation` は署名済みの包みと予約上限も含めます。保存後に送信待ちを取り消しても、確定済みの鍵を旧鍵へ戻しません。

第6b回では、鍵と失効の競合を次のように扱います（提案書 §5.1〜5.3）。通常の受信では、手元より大きい鍵版の包みだけを開きます。同じ鍵版の別の告知を受けても、その版の別鍵へ切り替えません。告知の commitment と実際の鍵の一致は、受信・保存の読み戻し・入り直しで共通に検査します。保存する `AdminRecordStore.Snapshot` に告知を加え、`SessionManager` の生成時にも保存鍵と照合します。告知の署名と参照本体は、受理した時点の管理者の権限を記録した履歴で読み戻します。あとから署名者が外されても、受理済みの記録は消しません。

第8b-2a回では、入り直しの旧overloadでも署名付き告知と対応する失効一覧を必須にします。まだ保存済み告知のない版5の初回移行だけは、手元のK/Vからcommitmentを照合します。保存済み告知がないのに引数に未保存告知を渡すことは拒否し、未検証のDHT告知や未知署名者の告知で比較の基準を作りません。保存済み告知がある場合も引数で基準を上書きせず、共有のKeyAnnouncement.checkKeyで鍵・版・同版commitment・順位を検査します。通常適用と保存復元も同じ照合を使い、保存復元へ受信時の現在時刻条件を追加しません。新しい招待による通常加入と版2〜5の読み込みは従来の互換を保ちます。

失効一覧の勝者と、拒否に使う和 R は別です。`AdminState.acceptRevocations` は、現在の管理者の署名・グループ・時刻を検証したあと、勝者が替わるか R が増えるときに true を返します。勝者より古い一覧でも新しい対象を含めば、その対象を R と署名済みの受領履歴に足し、勝者は替えません。古く、対象もすべて既知の一覧には false を返し、保存も R の追加もしません。X だけの一覧と Y だけの一覧は、どちらが先でも R に X/Y を残します。受領履歴の再生でも R を復元し、新しい空の一覧や署名者の削除で対象を復活させません。`RevocationUnion.restore` は、この検証済みの和を取り込みます。 R が上限に達したら、過去の失効を削って別の対象に入れ替えることはできません。 勝者にならない一覧を、R の増加だけを理由に履歴へ足す件数は、それぞれ新しい対象を1件以上足すため、R の上限65,536件以下です。勝者の更新だけで保存する一覧もあるので、履歴全体の件数やバイト数がこの値以下になるわけではありません。第7回では履歴全体を仮に65,536件、長さ接頭辞を含む履歴領域を12 MiBまでとし、管理平文全体16 MiBも別に検査します。履歴は削りません。失効65,536件と長い鎖・名簿・公開待ちを同時に保存できる保証ではありません。実際の保存量や上限到達の頻度を確認したとき、または履歴の詰め直しを別設計するときに、この仮値を見直します。state の包みは1 MiB・512 KiB警告のままです。

`KeyRotationCoordinator.observe` は署名と参照本体を検証してから、既知の最大の鍵版・失効版と、同じ鍵版の競合告知を覚えます。勝った失効一覧が R を欠く場合も統合を予約します。残るどの管理者でも、R を含む失効一覧を既知の最大失効版 +1 で署名し、新しい鍵を既知の最大鍵版 +1 で作って告知します。外された管理者や停止した管理者の復帰は待ちません。既存の包みの告知 digest は書き換えません。R に含む宛先には包みを作らず、証明書が無効な宛先にも渡しません。

`GroupAdministration.rotations` が管理者ごとに同じ調整処理を返します。Controllerと共有する入口では既存のCorePersistenceCoordinatorを渡し、同じSessionManagerへ二重登録しません。手動操作と統合は版番号の予約と5秒に1回の制限を共有し、別の取得で制限を回避できません。自分自身や、まだ BOUND の管理者であるメンバーの取り消しは断ります。統合では検証後に0〜2秒の乱数待ちを置き、同じ R と競合告知の組を保留1件にまとめます。期限は注入する単調時計、待ち時間と鍵の生成は注入する乱数で制御します。手動操作の間隔不足は `TOO_EARLY`、統合の待機中は `WAITING` です。 空でない取り消し対象がすべて R に入り、競合も R の統合も不要なら `IDLE` を返します。この重複操作では番号を予約せず、鍵も作り直さず、5秒の制限も消費しません。対象が空の明示の鍵入れ替えは、この重複判定とは分けます。保存に失敗した操作も番号を消費し、再試行で番号を再利用しません。いずれかの版が上限なら `VERSION_LIMIT` を返して止まります。

待っている間に、R を包含する失効本体と、より大きい版の告知・鍵を保存して採用できたら、保留候補と古い送信待ちを取り消します。取得済みの `Publication` も、取り消し後は内容を取り出せません。 保留中にさらに大きい版の競合を知ったら、取り消しの基準の版も上げます。途中の版の鍵を遅れて採用しても、より大きい版の競合を処理済みにはしません。処理済みにするのは採用した版以下の競合の組だけです。告知や包みが届いただけでは採用と数えません。R が増えた場合や現在の告知が変わった場合も古い送信待ちを外します。統合の保存は `CorePersistenceCoordinator` を通り、`PersistenceHooks.saveRotation` に管理状態・告知・鍵・包み・予約版を渡し、保存後にだけ公開します。`SavedRotation` と `restoreReservations`・`restorePublication` は再起動時の復元用で、保存鍵と署名・R・現在状態を照合します。第7回で予約版と署名済み送信待ちを管理ファイルへ保存します。署名候補を作る前に予約上限だけを通常保存し、以後の候補が失敗しても番号を戻しません。`KeyRotationCoordinator` の短い同期区間は予約と公開だけに使い、保存フックを呼ぶ間はそのロックを解放します。

入り直しの返事には、形式2の包みに対応する署名済み告知を項目8に、対応する失効一覧を既存の項目に必ず付けます。新しい `Joiner.rejoin` は手元の鍵・告知・R を受け取り、同じ版なら commitment と開いた鍵が手元と一致するときだけ通します。新しい握手鍵宛ての包みでも、同じ鍵なら入り直せます。告知 digest が違う再署名は、今の管理者の権限・署名・R の包含を満たし、手元の告知より順位を下げない場合だけ認めます。別鍵、告知の欠落、R の欠落、順位の後退は保存前に断り、旧状態を保ちます。旧 API は鍵を照合できないため、同じ版の入り直しを認めず、より大きい版だけを認めます。旧形式の返事の読み込みは残します。

新しいメンバーに渡す `JoinHandshake.Materials.verified` と `GroupAdministration.respondInvitation` でも、失効一覧が R を包含し、告知が鍵と一致することを要求します。最初の告知や現在の管理者による再署名が必要なら、鍵を知る管理者が作って保存してから返事を作ります。 この処理は `GroupAdministration.invitationMaterials` を共有します。初期告知の時刻は参照する管理者一覧と失効一覧の署名時刻の大きい方に固定し、同じ入力から同じ告知を作ります。告知のない保存形式5から再起動しても、同じ鍵と版・管理者鍵・参照本体なら、告知の内容と順位を変えずに作り直せます。`LanController` の発行と入り直しは検証済みの材料と新しい overload を使います。第6b回までは保存形式を変えず、第7回で告知も管理ファイルに引き継ぎます。R を欠く勝者一覧のまま招待の返事や鍵を発行しません。

DHT の勝者を選ぶ既存の順位は変えません。外された管理者による新しい一覧・告知と、外側の置き直しは `ManagedVerifier` が断ります。第8b-2b-i回の管理DHT受信では、DHT で OLD となった一覧でも、現在の権限と署名を検証できたものを失効の受信処理へ渡します。同じ鍵版の競合告知も、参照本体と署名を検証して `observe` へ渡します。DHT の勝者だけを渡して R や競合の情報を落とさないことが、呼び出し側の条件です。

第8b-2b-i回では、管理記録を既存のDHT STORE/VALUEとTransferで運びます。管理用はSyncEnvelopeのschema 3・DHT本文のschema 2、発見記録は従来のschema 2・本文1です。新しい項目やAdminControlの操作は足さず、管理封筒6は予約のままです。STOREは署名者と認証済みの送り手の対応を検証します。VALUEは要求した相手・現在のセッション・世代・要求番号・対象・元の期限へ結び、一度だけ返します。外側全体が768 Bを超えた記録はTransferを使い、全体の検証後にだけ管理記録の結果を返します。断片ACKは署名・保存の成功を意味しません。大きいVALUEは、元のRPC期限内に断片を受け、速度制限と予約の検査を通って組立が始まったときだけ、組立開始から240秒・進捗30秒の既存Transfer期限へ移します。最初の断片が速度制限や予約不足で捨てられた場合は、元のRPC期限を保ちます。進捗30秒・全体240秒の期限切れや、破損・全体検証の拒否で組立が終われば、要求も失敗として一度だけ終えます。同じ要求番号で組立を始め直さず、断片の再送で起点を変えません。壊れたDHTの封筒はその1通だけを断り、発見用と管理用のDHTは動作を続けます。

UDPの受信コールバックで共通の単調時計の時刻を記録し、保留を解く時は受信から30秒未満かつ既存組立の初回から240秒未満に限って処理します。保留の平文は受信から30秒以上で処理の対象から外れますが、保存中は `SyncInbox` から取り出さないため、その時点では消しません。実際のゼロ埋めは、保存が終わって最初に取り出し、期限を調べて破棄するときに行います。close・STORAGE_FAILEDでも消去します。保存中に保持する量は相手80件・全体256件・1 MiBの既存枠で有限です。組立開始・進捗にはその受信時刻を使い、保存後の現在時刻へ延長しません。組立が済んだ対象の完了ACKでは初回から240秒を調べ、保存中の進捗30秒は当てません。保存前から保留されていたACKも元の受信時刻で送り手の進捗を記録します。処理済みの保留平文と、破棄する未完組立の所有バッファも消去します。満杯なら捨て、待っているACK・再送・進捗の期限も延ばしません。復号は受信の番号の窓を進めるため、捨てた入力を同じ暗号文で受け直せません。送り手の新しい送信と、後段で接続する探索で補います（提案書§7.3・315行、2026-11-17の決定）。

RevocationRecoveryは、保存フックの取得より前に停止してもstorageBlockedを残します。フックは再取得しません。限定復旧が完了したときのinbox.clearは維持し、待っていた入力を再生しません。共通の成功記録は残り、後から届く正確な再送へ保存し直さず完了ACKを返します。

LanGroup.closeはstate.clearを先に行い、予約中なら所有する秘密を消す前に拒否します。tryCloseは予約の例外文だけを一か所で照合し、一致しない例外は再送出します。Controllerは拒否された所属を保持し、保存呼び出しの復帰時と次のpollで消去を再試行します。例外文への依存は、AdminStateを変更できる段で専用の例外型か照会口へ置き換える残件です。予約中にアプリが終了し、workerの終了後まで予約が残った場合は再試行できず、秘密がメモリに残る経路を許容します。半端な消去はしません。

失敗処理と消去も同じ解放保留を使い、予約で拒否されても失敗・消去の状態を反映します。解放保留中は自動再接続せず、解放後は保存済みの所属を読み直して新しい口を開けます。初回加入後の通常口が一時的に開けなかった場合も、保存済みの所属から接続を再試行できます。

再加入の入れ替え（LanController.pollのacceptRejoined後）で旧所属に予約が残る経路は、製品では未確認です。旧所属はjoinのstopNetworkでセッションと保存経路を止めてから保持し、通常の入れ替えでは予約がないことを試験しています。この経路の終了処理は今回変更せず、到達性が示された段でretiredGroupによる保留を設計します。新しい口の開始順序・終了・再試行の組み合わせを増やすため、現在の解放保留とは別の残件です。

### 5.2 URL と QR コード

- URL には、相手の宛先と、鍵を確かめる値を入れます（答え 17）。握手の鍵は短くせずに入れます（答え 20）。
- 待ち合わせのサーバーは置きません（答え 17）。
- 招待の URL と招待の QR コードの形は `distributak://join#<中身の base64url>` です（答え 89）。中身を `#` のあとに置くので、ブラウザに渡ってもサーバーには送られません。
- 中身は、管理者の EUD の番地、UDP の口の番号、握手の鍵（全部の長さ）、管理者の公開鍵、TOTP の秘密の値です（答え 89）。
- 鍵を確かめる値は、中身全体の BLAKE2s で、末尾に付けます（答え 89）。壊れたり打ち間違えたりした中身を見つけるためのもので、だれが作ったかを示すものではありません。
- 鍵を確かめる値は、BLAKE2s の出力を 16 バイト（128 ビット）にします（答え 115）。中身は Protocol Buffers で並べます。項目は作るときに `.proto` に書きます（答え 116）。
- 確かめる値は、**出力の長さを 16 バイトにした BLAKE2s** です（RFC 7693 の出力の長さの指定）。32 バイトの BLAKE2s の頭 16 バイトとは値が違うので、切り詰めて作りません（答え 126）。
- 中身の `.proto` は `core/src/main/proto/invitation.proto` の `Invitation`（proto3）です（答え 123）。ライブラリは `protobuf-javalite` 3.25.5 です（答え 124。references NW25）。

- DHT で見つけた相手（揮発の相手）は、ネットワークが変わったとき・セッションも握手も無いとき・証明書の検査に落ちたときに消します。鍵を 0 で埋め、経路・番地・速度の枠を消しますが、時刻の記録は残します。保存した相手の枠は、保存した相手を登録したときだけ 1 つ空けておきます（127 台と 1 台。登録が無ければ 128 台。上げる前は 31 台と 1 台）。pin が残る間は、DHT の相手とつなぎません（答え 182）。
- 線の形（答え 183）: DHT の項目（同期の包みの項目 9）は、同期の包みの版 2 だけで使います。相手が新しい版を話すかは、PING で探って確かめます。r19 の相手には、この探りの PING のほかは項目 9 を送りません。YES の相手でも、要求が続けて 3 回（仮の値）期限切れになったら分からないに戻し、上の回数の中で探り直します（答え 184 の 4）。探りは 0・60・180・420・900・1860 秒で、相手ごとに 24 時間で 12 回まで、全体で毎分 30 回までです（最初は毎分 6 回。模擬の結果で上げた。答え 192 (3)・193）。探りの回数の記録は相手の覚えとは別に持ち、相手を消しても・ネットワークが変わっても消しません（24 時間で消す。上限 1024 件）。
- STORE は、DHT を話すと分かった相手にだけ送ります。返事（STORE_RESULT）は、自分の出した STORE に合うものだけを受けます。形のおかしいもの・ほかのグループのものは、速度の枠を使う前に捨てます。FIND_NODE の続きは状態を持たずに返します。大きな物を分けて送る仕組み（Transfer）は作りますが、第12段では受けた転送の渡し先をつながず、捨てます。転送で受けた物は預かりの表にも答えにも載せません。CI では実際の UDP で 3 MiB を送る試験を 1 件行います。渡し先をつなぐのは、預かる物が発見の記録より広がるので、legal Q107 (2) と答え 181 の 6 の範囲を確かめてから別に決めます（答え 183 の 7）。転送は DHT を話すと分かった相手にだけ始めます。BLAKE2s の値が合わない転送には、全部受けたという ACK を返しません。断りの返事も速度の枠を通ってから返します（答え 184）。
- ログには、protobuf の型や中身を書きません（答え 166 (5)・183）。
- プラグインの配線（答え 196・197）: 発見の記録に署名する前に、必ず版を保存して予約します。予約できなければ出しません。入り直しの途中と、壁時計が負のときは版を取りません。配り直しは 1 時間ごとで、0〜5 分のばらつきを足します。時間は単調時計で数え、単調時計が戻ったら世代を進めます。DHT の仕事はコントローラーの作業スレッドの上だけで行い、核に新しいスレッドは作りません。ネットワークが変わったときと消去のときは、口を閉じる → DHT のメモリを捨てる → 保存を消す、の順にします。DHT のメモリを捨てるときは、経路表・揮発の相手に加えて、期限内のものも含めて預かっている記録を全部消します（例外で DHT だけ止めたときも同じ。答え 198 (5)・199）。揮発の相手で枠が埋まっているときに相手を保存すると、認証済みのパケットを最後に受けた時刻がいちばん古い揮発の相手を 1 台手放します（答え 198 (1)）。
- 画面（答え 196 (3)〜(6)）: 「DHT 経路表: N 預かり: N 検証で拒否: N」の 3 つの数と、「DHTを探し直す」のボタンを出します。ボタンは、押すたびに版を予約して署名し直し、1 つの相手に STORE → ACK → FIND_VALUE を送ります。返ってきた記録が、確かめた返事で、持ち主が自分・鍵が合う・版が今回 STORE した版と同じときだけ「DHT: 相手から自分の記録を受け取れました」と出します。ほかは「DHT: 見つかりませんでした」「DHT: DHT の相手がいません」「DHT: しばらく待ってから押してください」の決まった文です。押す間は単調時計で 60 秒あけます。logcat には数だけを出します。
- そのための核の口（答え 197）: 決まった相手 1 台に 1 回だけ FIND_VALUE を送る `findValueFrom`、STORE の受理（ACCEPTED・DUPLICATE）を true で返す `store(…, Consumer<Boolean>)` を足しました。どちらも結果は 1 回だけ渡し、待ちを捨てたときは null で 1 回渡します。ボタンの結果と配り直し（DhtPublisher）の結果は混ぜません。ボタンで受け取った記録は預かりの表に入れません。大きな転送で来た VALUE は、第12段では「見つかりませんでした」と扱います。
- 第13段（4.5）: 768 バイトを超える管理の記録（署名つきで 3 MiB まで）は、この Transfer で運びます。管理用の型だけを受ける渡し先をつなぎ、全体の署名を確かめてから一度だけ当てます。途中まで受けたものは当てません（ADR 0030 の答え 203 の 4）。

第8段（PRC-21.16）で、外の網で受ける前の備えを作りました。正本は ADR 0030 の答え 160 です。試験は PC のループバックだけで、値はどれも PC での試しの値です。外の網・Android の試験の前に見直します。

- **番地を確かめるクッキー**: `DTK` の 1 通目と、登録した招待への `DTJ` の頼みには、いつもクッキーを求めます。受ける側は新しい外枠 `DTC` 版 1 の CHALLENGE（80 バイト。1 通目のハッシュとクッキー）を送り元へ返し、送る側はクッキーと元の 1 通目を PROOF で包んで送り直します。クッキーは今ある HMAC-SHA256 で作り、30 秒未満だけ使えます。秘密は口ごとに持ち、60 秒で交代します（答え 160 の 1〜3・6）。
- **線の形**: `DTK` 版 1・`DTJ` 版 1 の線の形は変えません。PROOF の中身は 1184 バイト以下で、パケットは 1232 バイト以下です（答え 160 の 3）。
- **数の上限**: CHALLENGE を出す枠、MAC を確かめる枠、クッキーが正しかった包みだけが使う握手の枠の 3 段で数えます。握手の計算・HPKE・provider は、クッキーが正しく枠を通ったあとだけです。送り元ごとの記録は、クッキーが正しかった送り元にだけ作ります（答え 160 の 4・5）。
- **返事を送る相手**: 登録していない相手に握手の返事は送りません。状態を作らない CHALLENGE だけは包みの送り元へ返します（答え 158 の 4 を答え 160 の 7 で書き分けました）。第12段からは、DHT で見つけた相手でも、クッキーの PROOF と証明書の全部の検査（管理者の署名・失効・期限・握手の鍵の一致・身元の署名）を通った同じグループのメンバーには 2 通目を返します。それ以外には返しません。保存した相手の発行の順の検査は残します（答え 181 の 5）。
- **`refresh` の重さ**: 証明書と 2 つの一覧が同じオブジェクトの間だけ、Ed25519 の署名の検査結果を使い回します。失効・期限・時刻の幅は毎回確かめます（答え 160 の 8）。
- **閉じた合図**: 口が閉じたとき、理由を上の層の受け口に 1 回だけ知らせます（答え 160 の 9）。
- **残る危険**: でたらめな包みを毎秒 512 通より多く送られると、その間は新しい握手が通りにくくなります（答え 160 の 12）。

- 届いたかを確かめることと送り直すことは、CoT の版で行います（答え 56）。
- 1 つのパケットは 1232 バイトまで、DATA の平文は 1176 バイトまでです（3.4。答え 153 の 3・155）。
- 核の UDP の口（第6段）と、同じ口に載せた入るためだけの握手（第7段）の細目は 3.5 にあります。いまはループバックだけで試しています。`::` に結んだ 1 つのソケットで IPv4 と IPv6 の両方を受けることは第8段で作りました（IPv6 がない環境では作る処理が失敗し、`0.0.0.0` に結び直さない。答え 160 の 10）。Android で回線を選んで結ぶこと（bindSocket）はプラグインの段で決めます（答え 158 の 6）。

### 6.2 つなぐ順

1. IPv6 で直接つなぐ（答え 16）。
2. NAT の穴あけ（ポートの予測を含む）をする（答え 16）。
3. どちらでもつながらなければ、つながらないことを画面に出す（答え 16）。

- 中継は置きません。外の STUN サーバーも使いません。自分の外からの見え方は、相手から教えてもらいます（答え 16）。
- 穴あけの値は、仮に、0.5 秒ごとに送る、知らされた番号の前後 16 の口を予測する、20 秒であきらめる、とします（答え 90）。仮の値で、答え 47 の試験で直します。送る回数は、つながるか 20 秒たつまで送り続けます（各口に最大 40 回。答え 117）。

### 6.3 回線

- 回線ごとに、プラグインのソケットを Android の `Network` に結びつけます（`Network.bindSocket`。答え 43。NW12）。ソケットは、つなぐ前に結びつけます（NW12）。
- `bindSocket(DatagramSocket)` は API 22 から使えます（NW12）。プラグインが動く Android の API の下限は、使う版の ATAK の下限（minSdk）と同じにします。値は 23 です（ATAK 5.8.0.9 と同じ。公開の資料に値がなかったので、入れた ATAK の `dumpsys package` で確かめた。答え 77・132）。
- 優先度がいちばん高い回線 1 本で送り、切れたら次の回線に切り替えます（答え 42）。優先度は利用者が選びます（答え 7）。
- LAN の試験の段（第9段）では、ソケットを Wi-Fi の `Network` に結び、招待に載せる番地も Wi-Fi の IPv4 の番地だけにします（答え 162 の 1）。Wi-Fi が 2 本以上なら止めます。Wi-Fi が切れた・変わったら口と招待を閉じ、モバイル回線へは移さず、利用者の「接続する」でつなぎ直します（答え 163 の 6）。
- 第11段から、ATAK を起動し直したあとは、保存したグループがあり期限内なら自動でつなぎ直します（招待は持ち越しません。答え 178 の 2）。口が時計・乱数・受信の失敗で閉じたときも自動でつなぎ直します。待ちは 5・10・20・40・60 秒で、5 秒より速くしません。続けて 3 回失敗したら止め、利用者の「接続する」を待ちます（成功で数え直します）。Wi-Fi が切れた・変わった・利用者が止めた・`INTERNAL_FAILURE`・期限切れ・消去のときは自動でつなぎ直しません。

### 6.4 仮想の網の番地

- 番地は、端末の ID から IPv6 のユニークローカルアドレス（`fd00::/8`）を作ります（答え 58。NW15）。
- 割り当てる役は置きません（答え 58）。
- 番地は、`fd` に端末の ID（2 章）の頭の 120 ビットを続けたものです（答え 70。NW15）。65536 台でも、番地が重なるおそれは無視できるほど小さいとしています（答え 70）。

### 6.5 時刻

- 時刻は、EUD の時計（携帯網か GNSS で合わせたもの）を使います（答え 46）。
- 握手のときに測った相手との時刻の差は、画面に出すだけにします。差が大きいときは「時計を合わせて」と出します（答え 46・85）。
- 招待の 24 時間と、同じ返事を返す 10 秒（5.1）は、EUD の時計ではなく単調な時計で数えます（答え 130）。TOTP の値の計算だけは EUD の時計を使います。
- 自分の EUD の時計で比べるのは、期限（stale の時刻・証明書の期限・削除の印の期限）だけです。相手の言う時刻で期限が延びないようにするためです（答え 85・98）。ただし、次の項の版の時刻の上限だけは、自分の時計に対して判定します（答え 105）。
- CoT の版は、その CoT を作った EUD の時刻と、その EUD の ID です。版の順はこれで決めます（答え 42・98。7 章）。受ける EUD は、自分の時計より先すぎる版の時刻と、長すぎる stale の時刻に上限を付けます。上限を超えたものは断ります（答え 111）。上限は、版の時刻が自分の時計の 5 分先まで、stale の時刻が自分の時計の 30 日先までです（答え 105・112・122）。

## 8. 鍵の写しと消去

### 8.1 管理者の鍵の写し

- 写すのは管理者の鍵です。身元の鍵は出ません（答え 71）。
- 管理者がはっきり操作したときだけ、QR コードで取り出します。パスフレーズでは包みません（答え 30・31）。
- 戻すときは、別の端末の画面に出した QR コードを、プラグインのカメラで読み取ります。画像のファイルから読み込む口は持ちません（答え 34）。
- 1Password への保存は、利用者が手で行います（答え 32）。
- QR コードは、出してから 60 秒で自動で消します。もう一度出すには、改めて操作します（答え 79）。
- 管理者の鍵の写しの QR コードは、中身が秘密の鍵そのもの（答え 31）なので、招待の URL と同じ扱い（5.2。秘密の値を伏せる・クリップボードを消す・履歴に残さない・対面か相手を確かめられる経路だけで渡す）にします。すでにいるメンバーを見つける QR コードには当てません（答え 107）。
- 画面には「1Password」の名前を出さず、「パスワードの管理アプリ」のように書きます。この文書の説明では、これまでどおり 1Password と書きます。下の注意は画面に出す文なので、「パスワードの管理アプリ」と書きます（答え 83）。

QR コードを出す画面には、次の注意を出します。ADR 0030 の答え 30〜32 のあとに書いた注意で、決定ではありません（`02-functional-spec.md` の 8.1）。注意として出すもので、プラグインが止める機能ではありません。

- 画面に出している間は、人に見せない。
- 画面を写したときは、写した画像が Android のギャラリーと、写真のクラウドのバックアップに残りうる。パスワードの管理アプリに添付したら、端末とクラウドの両方から消す。
- 中身の文字列をパスワードの管理アプリに貼るときは、クリップボードに残りうる。


### 8.2 消去

- プラグインの「消去」の操作と、自分の失効を受けたときに、鍵とデータを消します（答え 46）。
- 消去では、Keystore の鍵を消します。包んだ鍵は、それで開けなくなります（答え 73）。
- 鍵のほかに、プラグインが持つもの全部（同期の記録、DHT の記録、削除の印、相手の一覧）を消します（答え 80）。ATAK の地図に出ている CoT は、ATAK の操作で消します。プラグインは消しません（答え 80）。
- 同期の記録のファイル `sync.bin` と、その一時ファイル（`.bak`・`.new`）も消します。初回の立ち直り（`initial.pending`）でも消します（答え 168 (6)）。
- DistribuTAK から受けて地図に入れた CoT も、消去と停止のあとに地図に残ります（答え 80・168 (2)）。受けた uid の記録と柵も消えるので、残った物は ATAK の標準の経路で外へ出ることがあります（制約。7 章）。
- 加入の確定やグループ作りが途中で止まったら、次の起動で止まる前の状態に戻ります（消去済みの端末なら消去済みのまま）。入り直し・作り直しはやり直します（答え 168 (8)）。
- 手で消去するときは、先にすべてのセッションを閉じ、つなぎ直しと待ち受けを止めてから消します。消したあとは、入り直すまでどこにもつなぎません。相手には知らせません（答え 99）。
- 消したあとは、利用者が新しい招待の URL か QR コードを読んで加入するか、新しいグループを作るまで、待ち受けもつなぎ直しもしません（答え 103・164）。
- 消したあとに作るグループは、元のグループとは別のグループです。グループの ID・管理者の鍵・グループの鍵・TOTP の秘密・端末の身元の鍵と握手の鍵・ポートをすべて新しく作ります。新しいグループの状態を包んで保存できたら「消去済み」の印を消します（答え 164）。
- 自分の失効を受けて消すときも、手で消すときと同じ順で消します（答え 104）。
- 消す順は、止める → Keystore の鍵を消す → ファイル・一時ファイル・相手・メモリを消す、です。メモリの中の鍵は、使い終わった配列を 0 で埋めます。String・Bitmap・暗号のライブラリの中の写しと、フラッシュの上書きは保証しません（答え 163 の 3）。

#### 第7回の保存形式6

版2〜5を読み込んだだけでは state を書き換えず、次の保存成功で版6へ進めます。身元鍵・握手鍵・管理者鍵・グループ鍵と版・証明書・保存相手・更新待ち・renewalCount・saveSeq・dhtLocalVersion・syncInitialized を引き継ぎます。同期と外来の印は移行で書き換えません。版6は既存の管理履歴の埋込み部分を、8バイトの管理世代と長さ付き32バイトの管理暗号化ファイル全体のBLAKE2s参照に置き換えます。整数は big endian です。

管理ファイルは `management-<世代>.bin` とし、世代ごとに新規作成・同期してから確定し、確定後は変更しません。既存のKeystore鍵と `StateEnvelope` の包みをそのまま使います。平文16 MiBにヘッダー・IV・tagの38Bを加えた上限を設けます。ディスクの空きは、新管理ファイル・stateの新旧と一時領域・settings・256Bの印を含めて検査します。世代採番では孤立・一時ファイルの番号も飛ばしますが、それらを権限の復元には使いません。stateが指定した1世代だけを読み、欠損・digest不一致・署名不一致なら止めます。旧世代の削除はstate切替より後です。

管理平文の形式1は、世代、受理順の全履歴と起点署名・勝者一覧・版・最新告知、和R、正確な名簿証明書、旧形式許可、旧管理者対応の根拠2通、端末内呼び名、管理者ごとの予約上限、署名済み送信待ち、停止理由、receivedRevocationCheckpoint を順に持ちます。バイト列と一覧は4バイトの長さ・件数を付け、文字列はDataOutputStreamのwriteUTF（2バイトの長さとmodified UTF-8）とし、負数・上限超過・余りを断ります。UNKNOWNを含むbindingは署名済み一覧そのものを保持します。名簿の初期値は検証済みの自分と保存相手だけです。セッション・未完探索・DHTで預かった他人の写し・経路は保存しません。Rは履歴の署名と当時の管理者権限を再検証して再構成し、保存した集合と一致させます。停止理由の欄は第7回では常に `NONE` です。起動時の停止の判定には停止印とcheckpointを使います。

第8a回の全ゼロtargetの復旧checkpointだけは管理平文の形式2を使います。形式1の末尾に、旧履歴の接頭件数（4B）・管理者版（8B）・失効版（8B）・長さ付き勝者一覧を追加します。旧targetと旧Rは既存のcheckpoint欄に保持します。形式1の読み込みを残し、この追加の根拠がない保存は従来どおり形式1で符号化して既存の候補digestを変えません。形式2はpreviousが全ゼロの候補なしtargetである場合だけ読み込み、previousの欠落や通常targetとの組合せは断ります。stateの版は6のままです。

通常保存の順は候補作成→管理確定→state参照の原子的切替→settings版3→核へ適用→送信です。旧形式で最初の失効を受信した場合も、旧状態を先に版6へ保存することはせず、固定領域の初期確保だけを済ませ、新受信候補のactiveを管理保存より前に確定します。失敗して旧形式stateが残ったときも、そのactiveから限定復旧の要件を読みます。settings版3は157Bで、旧版2の値に鍵版・正確な告知の符号化全体のdigest・commitment・管理世代/digestを足します。同じsaveSeqでは全項目を一致させ、stateが先ならsettingsを修復します。旧settings版1/2は旧来の意味で読みます。停止印とcheckpointの検査も別に行い、stateとsettingsを同時に戻した場合でも新しいclearと合わなければ通常起動しません。state・settings・印をすべて戻す攻撃は保存だけでは検出できません。

checkpoint は番号・確定saveSeq/管理世代・予定状態digest・Rのdigest・正確な受信一覧・その時点の履歴の接頭部分と勝者版への参照を持ちます。通常保存・番号予約・更新・入り直しではそのまま引き継ぎます。clearは最新state全体との一致ではなく、checkpointとの一致、state.saveSeq以上、現在Rによる包含、残存する署名根拠で検証します。候補digestは固定ASCII用途ラベル `DistribuTAK/state-candidate/v6`、管理参照digestを0にしたstate本体、checkpoint自身のtarget_state_digestを0にした管理平文をこの順に、各々4バイトbig endianの長さを付けて並べ、BLAKE2sを取ります。既存の暗号・署名の用途ラベルは変えません。

受信した失効で、履歴の件数・バイト数や管理平文16 MiBの上限により候補自体を作れないときは、target_state_digest と target_R_digest をともに全ゼロとする「候補なし」のactiveを確定します。required_revocation_versionは検証済みの受信一覧の版、target_saveSeqは現在のsaveSeqです。全ゼロtargetは確定候補の証拠にならず、起動時も通常保存やclearでも停止を解除しません。履歴を削って保存を成功させず、固定文「保存がいっぱい」を保ちます。候補を作れるときは、予定digestを決めてactiveを確定したあとに空き容量を検査します。

第8a回では、有効なactiveの予定失効がstateにない場合と、全ゼロtargetの場合に限定復旧へ進みます。取り直した署名済み一覧の版がrequired_revocation_version以上で、保存済みRを包含することを要求します。全ゼロtargetを候補との一致に使いません。元のtarget全体、復旧前の署名済み履歴の接頭部分・勝者一覧・管理者版・失効版、再構成したRを新checkpointへ結びます。再起動でも署名と当時の権限を検証して旧Rを再構成し、保存した集合との一致と新一覧による包含を確かめます。証拠がなければclearへ進まず、再取得または停止を保ちます。復旧後も履歴65,536件・12 MiB、管理平文16 MiBの仮の上限を越えるなら、履歴を削らず停止を保ちます。

停止印 `stop-marker.bin` は移行前に256Bを実際に書いて同期し、128Bを2スロット使います。初回確保はファイルと親ディレクトリの両方を同期し、どちらかが失敗したら確保完了としません。magicはDTSM、形式1、flagはclear=0/active=1、reasonは受信失効=1/復旧保存=2、予約は0です。write_seq・target_saveSeq・required_revocation_versionを各8B、状態digest・Rのdigest・先頭96Bのchecksumを各32B持ちます。checksumは破損検出です。古いスロットから同じ場所へ上書きし、各スロットでwrite_seqを1増やします。一時ファイルやrenameで印を置き換えません。active/clearは最初を含め3回、失敗後100ms空け、同期まで成功した場合だけ確定します。全回失敗なら停止します。activeを書けず旧clearだけを残して落ちた場合は、再起動後停止の保証から除く決定Bを保ちます。

| クラッシュ点・起動時の状態 | 採る処理 |
|---|---|
| 管理確定前・state切替前 | 旧stateを保つ。active確定済みなら限定復旧の要件を得て通常通信を止める |
| 管理確定後・state切替前 | 未参照世代を復元しない。旧参照先を残す |
| state切替後・settings前後 | 新stateを正とし、settingsを修復する |
| active書込み前後・片側だけ更新 | 新しい有効なactiveを優先し、旧clearへ戻さない |
| 新失効保存後・clear前後 | 保存相手と更新待ちを整理する前のstateでsaveSeq/確定管理世代・候補全体digest・R・受信署名根拠が合うときだけ両clearへ確定する |
| 通常保存後の古いclear | 引継いだcheckpointとR包含を検査し、最新候補全体との一致は要求しない |
| U1復旧保存後・新active/clearの途中 | 旧activeの全targetと包含の根拠を結んだ復旧checkpointを検証してから新active→clearへ進む |
| 欠損・破損・相反する印・根拠不足 | 停止し、壊れた印から版の下限や集合を推測しない |

版6は期限切れの更新待ちも、候補全体のdigestを照合するために読み込みで捨てずに残します（捨てるとdigestがずれて止まるため）。第8a回では、旧形式の更新待ちが現在の基準と合わなくなった場合も元の符号化を停止印の検査まで保ち、その後に無効な値を取り除きます。新形式の壊れた値は従来どおり保存全体を断ります。残した更新待ちは通信の許可にならず、相手の登録時に通常の証明書検査を通らなければ使われません。また、失効した保存相手の根拠だけを検証する緩い検査は、版6の通常保存にも掛かります。失効相手を含む状態が保存されても、次の読み込みで整理前のstateの照合のあとに取り除きます（第7回のFable第3回レビューの軽微1・2。挙動は変えず、この文書に記録）。

版2〜5の通常通信を新しく始める前に、初期clearの固定領域を確保します。この準備だけではstateを書き換えません。初回移行の管理保存や仮保存が失敗し、初期clearだけが残った場合は、検証した旧Rと版が一致するclearに限って再試行の候補へ更新します。版2〜5が正と検証でき、初期確保の途中の領域だけが残った場合は、部分の領域を権限の根拠にせず、同じ場所を実際に確保し直して同期します。有効なactiveスロットがあれば上書きせず止めます。版6の壊れた印には、この初期化の道を使いません。通常稼働中の版5で確保に失敗した場合は、移行を確定せず旧状態と既存口を保ち、STORAGE_FAILEDにも「保存がいっぱい」にもしません。確保が済むまでは再起動・再接続で新しい口を開きません。次の通常保存で確保を再試行します。失効を受信した場合は別で、activeを確定できなければ核がSTORAGE_FAILEDへ閉じます（提案書350行、2026-11-16の決定Bの補足）。U1では元のactiveを復旧保存完了まで保持します。旧集合を再構成できればdigestと包含を、できなければ取り直した署名済み一覧の集合digestの完全一致を証明します。元の予定状態digestと同じだと偽らず、旧target全体と必要なら再構成した集合を新checkpointへ保存します。第8a回のControllerは、検証できた復旧要件があるときだけ限定復旧用のUDP口を開きます。通常の同期・DHTや管理操作はclearの同期と現在の通信権限の再検査が終わるまで始めません。復旧要件を検証できない破損した印では口を開きません。通常保存のstage／saveSnapshotとactiveのフックは、停止中の既存activeを上書きしません。

Controllerの通常保存は `saveUnchanged` でPERSISTINGへ入り、保存I/OをUDP口・sessions・AdminStateのロックの外で行います。正常な保存の前後にstop/closeを呼びません。非失効セッション・鍵・元の期限をメモリに残し、180秒・進捗30秒・全体240秒を保存時間で延ばしません。保存中も期限の整理を続け、期限切れを保存後に復活させません。

第8b-1回の通常失効ページも、核の受信保存からactive→管理保存→state切替→clear同期へ進みます。Controllerの `saving` をこの外側に重ねません。保存失敗後は固定文「保存がいっぱい」で止め、再起動では従来の停止印の検証と限定復旧を使います。完了ACKの再送用の成功記録はメモリだけに置き、state・管理ファイル・停止印の形式は変えません。

版6保存後の旧APKへの差し戻しは禁止です。運用の手順は [保存形式6への移行](state-v6-migration.md) を参照してください。
