# DistribuTAK の設計書

DistribuTAK は、ATAK のプラグインです。同じ鍵グループの EUD（Android の端末）どうしが、LAN・WAN・モバイル回線の上で CoT を同期し、各 EUD が分散型の TAK サーバーの役を持ちます。本機（PRC-163 風機）が無くても動きます。根拠は ADR 0030（`PRC-163:docs/decisions/0030-device-as-lan-router.md`）です。

本機の操作（ext-link）と、本機の無線で送る CoT（LoRa のように IP を通さない経路の分）は、別のプラグイン RadioLink が受け持ちます（ADR 0030 の答え 10・39・40）。RadioLink の設計は、この文書の組に入れません。

この文書の組は、もとは PRC-163 の `docs/distributak/` に置いていました（2026-11-11 に利用者が決めた。ADR 0030 の答え 49）。2026-11-16 に、このリポジトリの `docs/` へ分けました。

## 2. ADR 0030 の番号の引き方

ADR 0030 には番号の付いた並びが 2 つあり、1〜4 が重なります。この文書の組では、次のように書き分けます。

| 書き方 | 指すもの | ADR 0030 の節 |
|---|---|---|
| 網の見方 1〜4 | 本機と MPU-5 風機を LAN のルーター・スイッチとみなすことなど | 「決定」 |
| 答え 1〜107 | 未決（U-NW-1〜5 と細目）への利用者の答え | 「未決への利用者の答え」の「これで決まったこと」 |

ADR 0030 の本文は、答えのほうも「決定 N」と書いています（例: 答え 39 の「決定 10」は答え 10 のこと）。この文書の組から引くときは「答え N」と書きます。

## 4. 守ること

この文書の組の中身は、CLAUDE.md の「法的ガードレール」に従います。とくに次のことは、DistribuTAK の設計でも変えません。

- ADR 0030 の「変えないこと」はそのまま守る。HaLow のブリッジは legal Q99 (4)(5) を確かめるまで有効にしない。本機の `usb0` は転送しない。答え 35〜37 は、legal の確認が済んでから行うこととして書く。
- 送信ゲートは SCU の 1 か所。EUD から R/T1・R/T2 に出すデータは送信ゲートを通す。DistribuTAK にも RadioLink にも、本機の送信を許す口は作らない（答え 40）。
- 暗号は公開の標準と、よく知られた実装のライブラリだけを使う（答え 14・19・20・33）。
- DistribuTAK の名前・画面・設定には、本機の名前を出さない（答え 7・10）。商標は製品・画面に入れない。
- ATAK の SDK・ATAK-CIV のコードをリポジトリに入れない。SDK の例を写さない。SDK・takdev の jar を逆アセンブルしない。署名の検査を迂回する方法を調べない・作らない。例のキーストアの合言葉を文書に書かない（引き継ぎ 6 章）。
- 送る・上げる・フォームに入れる前には利用者に確かめる。tak.gov へは利用者が自分で上げる（引き継ぎ 6 章）。

## 5. ADR 0030 の影響の表の進み具合

ADR 0030 の「影響」の表（13 行）を 1 行ずつ処理し、直したか、直さない理由をここに書きます（PRC-21.6 の受入基準 #3）。

13 行はどれも本機の文書で、この文書の組の外にあります。2026-11-11 に、決まったところは各文書に「〔ADR 0030（2026-11-11）: …〕」の注記を入れました。決めた時の文は記録として残し、本文の書き換えは、細目が決まって設計を進めるときに行います。細目が残るところは保留にし、根拠と、保留を解く条件を下の表に書きました。保留を解く条件が「利用者の決定」のものは、6.1 にも挙げています。

進み具合の言葉は次の意味です。

- 直した: 決まったことを注記で入れた。その行で残る未決はない。
- 一部を直した: 決まったところは注記で入れた。残りは保留。
- 保留: まだ直さない。根拠と、保留を解く条件を書いた。
- 変えない: 決まりを変えない制約の行。

## 6. 確かめること

決まっていないことは推測で埋めません。利用者に確かめ、答えを先に ADR 0030（答え 50 から）に書いてから、この文書の組に使います。法令に関わるものは `PRC-163:docs/legal.md` の要確認事項にも書きます。

### 6.1 まだ決まっていないこと

- 本機の有線の WAN の口は USB に決まった（答え 118）。usb0（EUD 用。転送しない）との分け方は決まっていない。本機の側の話で、DistribuTAK の設計には響かない。
- 答え 38 で受け持つ機能の一覧と、ext-link を USB だけに残すか IP でも届けるか（利用者が動画 NW13 を見てから決める）。RadioLink と本機の側の話。
- RadioLink の商標の検索（答え 39）と、RadioLink のほかの細目。RadioLink は別のプラグインなので、RadioLink の設計を進めるまで未決が残ってよい（2026-11-11 の利用者の指示）。
- 本機の側で D6 の口をなくしたあとのこと（5 章の 2〜4 行目。どれも利用者の決定を待つ。RadioLink の細目と一緒に決めてよい）:
  - 本機が ATAK の既定の CoT の口（06 12.7.2）を受け続けるか、RadioLink からどの口で受けるか。
  - D6 を使っていた追いつき・マーカー・ファイル・つなぎ役のうち、どこまでを RadioLink と `datad` に残すか（06 12.7.3、F07 3.3）。D6 を通さないときの EUD のファイルの受け渡し（ADR 0021 の決定 4）も含む。

### 6.2 設計書を書く中で確かめて決まったこと

2026-11-11 に利用者に確かめ、ADR 0030 の答え 50〜122 に書いた。

- パッケージ名は DistribuTAK・RadioLink とも新しい名前にし、頭は GitHub のアカウントから作る（答え 50。PRC-21.6 の受入基準 #4）。
- `ext-link.proto` の enum `RadioLink` の名前を変える（答え 51。型の名前は `PhysicalLink`、値の名前は `PHYSICAL_LINK_*`。値の番号は変えない。書き換えは作業者が行う。Backlog の PRC-21.7）。
- 答え 16 の「中継は置かない」と答え 42 の配り直しは、層が違うので両立する（答え 52）。
- TOTP は前後 1 刻みまで受ける。握手の時刻の値は相手ごとに増えていればよい（答え 53）。
- 削除の印は 30 日残す（答え 54）。ホップ数の上限は仮の値で 16（答え 55）。
- プラグインが開く口は UDP の口 1 つ。既定の番号は設定で変えられる（答え 56）。既定の番号は、プラグインを入れたときに 49152〜65535 から乱数で決める（答え 65）。
- グループの中の DHT は Kademlia の方式（答え 57）。
- 仮想の網の番地は、端末の ID から IPv6 のユニークローカルアドレスを作る（答え 58）。
- 人を外したあとの新しいグループの鍵は、管理者が 1 人ずつ HPKE で包んで署名し、DHT で配る（答え 59。暗号を足すので legal Q107 (6) で一緒に確かめる）。
- 新しいメンバー、新しいグループの鍵を受け取れなかったメンバー、証明書の期限が切れた EUD は、TOTP の URL で管理者の EUD へ直接つなぐ「入り直しの手順」で入る（答え 60〜62）。
- DistribuTAK のグループは、本機の鍵グループ（ADR 0024）とは別のもの（答え 63）。
- hide の印は `<__share scope="group"/>` に変え、古い印は読まない（答え 64・68）。
- Kademlia の値は論文の値を仮に使う（k = 20、α = 3、寿命 24 時間、1 時間ごと。答え 66）。
- HPKE は DHKEM(X25519, HKDF-SHA256)・HKDF-SHA256・AES-128-GCM、base モード（答え 67）。
- TOTP は 8 桁・SHA-256。秘密の値は管理者の EUD が招待ごとに作る（答え 69）。
- 端末の ID は身元の鍵の公開鍵の BLAKE2s-256。番地は `fd` と ID の頭の 120 ビット（答え 70）。
- 管理者の鍵は、管理者ごとに身元の鍵とは別の Ed25519（答え 71）。
- 暗号のライブラリは Bouncy Castle にまとめる（答え 72。legal Q100 (b)・Q107 (6) も同じ変更で直した）。
- 鍵は Android の Keystore の取り出せない AES の鍵で包んでしまう（答え 73）。
- 握手のあとの鍵は WireGuard の値で作り直す（答え 74）。
- 管理者が署名して DHT で配る記録には、署名の中に版の番号を付ける（答え 75）。

- 招待の URL と招待の QR コードは、対面で QR コードを見せるか、相手を確かめられる経路だけで渡す。画面では秘密の値を伏せ、クリップボードは短い時間で消し、履歴に残さない（答え 92）。

- 入り直しの鎖に要る管理者の一覧は、招待した管理者の EUD が、URL を作ったときの版からいちばん新しい版まで残し、入るためだけの握手の返事に入れて送る。招待を消すときに消す（答え 101）。
- 握手を受ける側は、2 通目に自分の証明書を入れる。始めた側は、それを 1 通目と同じ検査で確かめてから CoT などを送る（答え 102）。
- 手で消去したあとは、利用者が新しい招待の URL か QR コードを読んだときにだけ、入るためだけの握手を始める。それまでは待ち受けもしない（答え 103）。
- 自分の失効を受けて消去するときも、手で消去するときと同じ順で消す（答え 104）。
- 答え 164 で改めた: 消去を終えたあとは、新しい招待で加入するほかに、元のグループとは別の新しいグループ（ID・鍵・TOTP の秘密・端末の ID・ポートをすべて新しく作る）をすぐに作れる。どちらかを選ぶまでは待ち受けもしない。
- 将来、1 台の EUD が複数のグループに同時に入れるようにする。異なるグループの間では自分のデータだけを送り、あるグループから受けたほかのメンバーのデータを別のグループに送らない（答え 164 (5)）。
- 複数のグループの細目（答え 165。作るのは後の段）: 自分のデータは、自分の位置と自分の ATAK で作った物だけ（他人の物を書き換えたもの・ほかの網から受けた物は含めない）。他人のデータは手で選んでも別のグループに送らない。位置を送るかはグループごとに設定し、作った物は送るグループを選ぶ（既定は、いま選んでいるグループだけ）。鍵・端末の ID・ポート・保存・DHT はグループごとにすべて分け、別のグループからは同じ端末だと分からないようにする。確かめは送信の口の手前の 1 か所にまとめる。
- 受ける EUD は、先すぎる CoT の版の時刻と長すぎる stale の時刻に上限を付ける。上限を超えたものは断る。上限は、版の時刻が 5 分先まで、stale の時刻が 30 日先まで。どちらも受ける EUD の時計から数える（答え 105・111・112・122）。
- 同じ返事を返すため、管理者の EUD は、入る側の鍵・使った TOTP の値・出した返事を、その時間のあいだだけ残し、消去でも消す（答え 106）。
- 答え 92 の扱いは、管理者の鍵の写しの QR コードにも当てる。メンバーを見つける QR コードには当てない（答え 107）。

- 招待の URL を作るとき、URL を作る管理者は、そのときの版の管理者の一覧に自分の署名を添えて残す。入る側はこの署名で最初の一覧を確かめ、そこから鎖をたどる（答え 109）。
