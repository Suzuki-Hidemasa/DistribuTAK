# レビューの討論の手順（Astra と Fable の二者）

PRC-163 の ADR 0014 の体制を、2026-11-16 に DistribuTAK へ引き継いだ。
レビューは GPT-6-Astra（high。agmsg の名前 `astra-reviewer`）と Fable 5.2（medium。`fable-reviewer`）の二者が討論して、結論を出す。Claude のレビュアーは Fable 5.2・medium に固定する（使用料のため high にしない。Opus は使わない）。
オーケストレーター（`claude`）は依頼と結論の受け取りだけをし、討論には入らない。

## 1. 置き場所

レビューごとに ID（`YYYYMMDD-題名`。例 `20261116-distributak-stage13-r3fix`）を決め、レビューする場所（ワークツリー）の
`out/reviews/<ID>/` にファイルを置く（`out/` は git に入らない）。

| ファイル | 書く人 | 中身 |
|---|---|---|
| `request.md` | オーケストレーター | 対象（ブランチ・コミット・`git diff` の範囲）、見てほしい観点、関係するドキュメント、締め切りの目安 |
| `r1-<名前>.md` | 各レビュアー | 1回目: 独立して見つけた指摘 |
| `r2-<名前>.md` | 各レビュアー | 2回目: 相手の指摘への同意・反対と、自分の指摘の取り下げ |
| `conclusion.md` | `fable-reviewer` が下書きし、`astra-reviewer` が合意する | 結論 |

## 2. 指摘の書き方

指摘ごとに次を書く。根拠のない指摘は書かない（推測で書かない）。

```
### <番号>. <一文の要約>
- 重要度: 必修 / 推奨 / 軽微
- 箇所: <ファイル>:<行>（ドキュメントなら節）
- 根拠: <要件・仕様・設計・ADR の該当箇所、実行したコマンドと結果>
- 失敗の筋書き: <どういう入力・状態で、何がどう悪くなるか>
- 直し方の案: <あれば>
```

- `CLAUDE.md` の「ガードレール」に反するもの（SDK のコードの取り込み、新しい暗号方式、HPKE の info/aad・署名の接頭辞の変更、秘密・端末の識別子の混入、実機への操作など）は、必ず**必修**にする。
- ドキュメントで決まっていないために判断できない点は、指摘ではなく「未決」として別に書く（利用者への確認の候補）。
- 秘密（鍵・招待の URL・TOTP・PSK・キーストアのパスワード）を指摘や結論に書き写さない。場所と種類だけを書く。

## 3. 進め方

1. **1回目（独立）**: `request.md` を読み、相手の `r1` を読まずに `r1-<自分>.md` を書く。書き終えたら、相手に
   「r1 完了: <パス>」を送る。
2. **2回目（突き合わせ）**: 相手の `r1` を読み、相手の指摘のそれぞれに「同意」「反対（根拠）」「要確認（何を確かめれば決まるか）」を付ける。
   相手の指摘を見て自分の指摘を取り下げるなら、その理由を書く。`r2-<自分>.md` に書き、相手に「r2 完了: <パス>」を送る。
3. **3回目（残った食い違いだけ）**: まだ食い違う点だけを、agmsg で短く（1点につき1往復まで）やり取りする。新しい根拠がなければ、そこで打ち切る。
4. **結論**: `fable-reviewer` が `conclusion.md` を下書きし、`astra-reviewer` に送る。`astra-reviewer` は「合意」か直してほしい点を返す（直しは1回まで）。
   合意したら、二者がそれぞれ `claude` に「結論 <パス>（合意）」を送る。

討論は3回目で必ず終える。決着しない点は、そのまま結論の「合意できなかった点」に書く。

### 相手が応答しないとき

- 相手に送ってから 15 分たっても返事がなければ、もう一度短く送る。Codex（astra-reviewer）が相手なら `tools/agents/nudge.sh astra-reviewer` も1回使う。
- さらに 15 分たっても返事がなければ、`claude` に「応答なし（相手・最後に送ったもの・いまの段階）」を送り、自分の分だけで結論の下書きを作って待つ。
- オーケストレーターは、`request.md` の締め切り（書いていなければ 40 分）を過ぎたら様子を確かめ、動かなければ利用者に知らせる。
- Claude Code の受信の監視（Monitor）は時間で切れる。切れたら張り直す（`fable-reviewer` のスキル）。

## 4. 結論（conclusion.md）の形

```
# レビューの結論 <ID>（対象 <ブランチ・コミット>）

## 合意した指摘（重要度の順）
### 必修
### 推奨
### 軽微

## 合意できなかった点
- <点>: astra-reviewer の主張と根拠 / fable-reviewer の主張と根拠 / 決めるのに要るもの

## 未決（ドキュメントで決まっていない点。利用者への確認の候補）

## 確かめたこと
- <実行したコマンドと結果（核・プラグインの試験、lint、NewApi など）>
```

## 5. 決まり

- レビュアーはリポジトリのファイルを変えない（`out/reviews/<ID>/` に書くだけ）。コミット・push・ブランチの切り替えもしない。
- 試験などのコマンドは実行してよい。生成物は `out/` に出す。
- レビュアーは実機に触れない。
- agmsg の本文はファイルから送る（`tools/agents/send-file.sh`）。Codex は返事を `tools/agents/wait-msg.sh` で待つ。
- 合意できなかった点は、オーケストレーターがドキュメントをもとに決める。ドキュメントで決まっていなければ、利用者に確認する。
- Codex の使用量が足りないときは、`fable-reviewer`（Fable 5.2・medium。`spawn-agent.sh fable-reviewer --solo`）の一者だけでレビューし、一者で結論を `conclusion.md` に書いて claude に送る。このときは 6 章の表に書かなくてよい（決まった体制のため）。

## 6. 例外の記録
